# Interface catalog

Status: canonical | Owner: architecture | Last verified: 2026-08-13

Shared Zod schemas own every current request and response shape: event mutations/lists/basic metadata, agenda draft/placement/publication/public projection, current session/capabilities, demo session, health, and the standard error envelope. They generate [`packages/contracts/openapi.json`](../../packages/contracts/openapi.json), and CI rejects drift. The OpenAPI document covers health, the internal demo-cookie route, session, event, agenda, and public-schedule routes, cookie security, and implemented success/error statuses. Domain types own business semantics. Drizzle declares intended storage, immutable SQL migrations own deployed history, and the D1 adapter owns persistence behavior. Explicit tested mappers connect transport, domain, and storage models.

## Route groups

- `API-AUTH-*`: session, seeded demo identity switch, current capabilities, membership and invitation administration, and organization API clients.
- `API-ORG-*`, `API-EVENT-*`: organization/event commands and queries.
- `API-CFP-*`, `API-REVIEW-*`: forms, submissions, assignments, evaluations.
- `API-CONTENT-*`, `API-CRM-*`: speakers, sessions, tasks/assets, prospects/activity/conversion.
- `API-AGENDA-*`: rooms, tracks, placements, conflicts.
- `API-COMMS-*`, `API-INTEGRATION-*`: templates, outbox, attempts, projection state.
- `API-PUBLIC-*`: published hub, schedule, sessions, speakers, and CFP/embed reads.
- `API-OPS-*`: cross-domain operational reads owned by platform — the organizer overview and the
  permission-aware event search.

Implemented review routes are `GET /api/events/{eventId}/review/organizer`, `PUT /api/events/{eventId}/review/statuses`, `PUT /api/events/{eventId}/review/plan`, `POST /api/events/{eventId}/review/assignments`, `POST /api/events/{eventId}/review/transitions`, `POST /api/events/{eventId}/review/decisions`, `GET /api/events/{eventId}/review/assignments`, `DELETE /api/events/{eventId}/review/assignments/{assignmentId}`, `POST /api/events/{eventId}/review/assignments/{assignmentId}/conflict`, and `PUT /api/events/{eventId}/review/assignments/{assignmentId}/evaluation`. The transitions endpoint has an all-or-nothing atomic contract and refuses the two reserved decision statuses outright, naming the decisions endpoint: reaching `accepted`/`declined` is the effect of a recorded decision, and a transition into one wrote a status with no decision behind it. The statuses endpoint completes rather than refuses a set that omits the reserved decision statuses, and every status the organizer projection advertises is stored, so anything it offers is reachable — the pipeline steps by a transition, the two reserved outcomes by a decision. Removing an assignment is `DELETE` on the assignment: it takes any draft evaluation and declared conflict with it, releases the rubric lock that the existence of an assignment holds, and is refused once that reviewer has completed an evaluation whose score is already counted in the aggregate. The decisions endpoint records the accept/decline decision and, for an accepted outcome, composes the content acceptance in the same request; the two are not one transaction, so each proposal's `acceptances` entry reports `content` with its session id or `decision_only` with the content domain's own field errors. A `decision_only` outcome leaves the decision durable and is repaired by posting the identical decision again. Reviewer assignment validates the named user's event reviewer role. Evaluation completion is terminal, retry-repairable, and atomically writes the evaluation, aggregate, and unique versioned completion event. The reviewer assignment response deliberately omits aggregate outcomes. Shared Zod schemas define every body and response and generate the OpenAPI artifact.

Agenda draft routes are scoped below `/api/events/{eventId}/agenda` and require `agenda:manage` plus either an event organizer role or organizer membership in the event's owning organization. Resource `PUT` initializes or replaces rooms, tracks, and slots while rejecting deletion of an in-use resource. Placement `PUT` is idempotent by placement ID and uses optimistic revision retries to preserve concurrent edits; `DELETE` removes a placement with the same protection. Every draft response carries `occurrences`, two maps naming the board revision at which each session's placements last changed and at which each time slot was last retimed, and every conflict carries the later of its two placements' and its two slots' as `occurrence`; all of them advance inside the same optimistic write, so a lost update re-derives them against the board that actually committed. A slot's number moves on a change of *instant*, so re-spelling `16:00:00.000Z` as `16:00:00Z` is not a retiming. Rooms, tracks, and slots being added or removed carry no number, deliberately: no derived condition reads any of them — an overlap is decided by slot times and by ids the placements already carry — and counting them would resurface decisions about conditions an added room or an empty new slot cannot affect. A board stored before the numbers existed answers zero for everything — the read normalizes, so the field is present on every response including the one an assisted pass that seats nothing returns. They exist for consumers that store a decision about a *derived* condition — the operational inbox's dismissals — and describe the draft rather than the programme, so a publication snapshot carries neither them nor the conflicts. `POST /agenda/assisted-placements` seats every unscheduled session — or the `sessionIds` named in the body, which may be omitted entirely to mean all of them — in one request and one draft revision, choosing the earliest free slot and the first configured room that adds no conflict by the same `conflictsFor` rule the board displays and publication refuses on. It is deterministic for a given board — sessions are ordered by title then id and cells by time then configured room, both total orders computed by the agenda rather than inherited from a query — gives each session a placement id derived from the session so re-running converges rather than duplicating, never moves a placement the organizer made by hand, and returns the ordinary draft plus a `placed` list naming the sessions this pass seated and an `unplaced` list naming each session it could not seat and why. `placed` is reported rather than left to be inferred: the board in the same response also carries whatever another organizer committed while the request was in flight, so a client comparing the board it sent with the board it received cannot tell this action's work from theirs. The result is draft state: it reaches no public surface until `POST /publications`. `POST /publications` rejects conflicts with `AGENDA_CONFLICT` and resource-specific explanations. Versions are allocated by attempt rather than reserved: the command reads the version in force, tries to commit the next one, and retries against a fresh read when a concurrent publication took it first, so simultaneous publications produce distinct, monotonically increasing immutable versions with none lost and no snapshot overwritten. The publication and the `EVT-SCHEDULE-PUBLISHED` record announcing it are written in one D1 batch, so a failure leaves neither. Losing the allocation race five times running is reported as `CONFLICT` — contention to retry, not a malformed request. An optional `Idempotency-Key` request header makes the command idempotent: the same key on the same event returns the publication the first attempt committed, including when the board has since moved into conflict, so a client that never saw the first response does not freeze a second identical version. Omitting the header means a new intent and allocates a new version, which is what pressing Publish again after editing means; unkeyed publications never collide with one another. `GET /api/public/events/{slug}/schedule` requires no session and returns the latest immutable publication's `version` and `publishedAt` — never its audit-only actor identity — together with the sessions the event's published projection places, each under the public slug that projection assigned and carrying its title, abstract, format, track, speaker slugs, room, and start/end instants. The agenda snapshot itself is not serialized: it covers the organizer's whole board, including sessions whose content is still a draft, and is keyed by storage identifiers, so nothing but the publication's identity crosses that boundary. A published session with no placement is not on the schedule; it remains on the event hub. The placement detail is the projection's own copy, so the schedule and the hub always agree about a session; republishing the agenda advances `version` before that detail follows, exactly as every other source moves ahead of the snapshot until the site is published again. The route is addressed by the event's public slug and gated on the publication being live: an unknown slug, an unpublished event, and an event whose agenda was never published all return the same `NOT_FOUND` "This event is not published." envelope, so unpublishing retracts the schedule along with the rest of the public surface. The agenda derives the `EVT-SCHEDULE-PUBLISHED` v1 payload from every committed publication and commits it in the publication's own batch, and a writer is now bound to that seam: communications' `event` channel carries a domain event with no provider on the other end, so the record is durably stored in that same batch rather than derived and dropped. Its key is the event's own derived id, so a replayed publish command produces one record and a genuinely new publication produces another. Draining it fans out one schedule confirmation per reachable speaker, idempotently per `(event, publication version, speaker)`, so the at-least-once outbox writes to nobody twice.

Migration `0002_identity_event_foundation.sql` preserves pre-foundation events under a stable imported organization and assigns the seeded organizer membership/event roles before adding organization scope. Deterministic reset replaces that imported state with the role-complete local fixture.
Content routes are defined by the generated OpenAPI contract. `POST /api/events/{eventId}/content/accept` atomically consumes a proposal/review outcome without reading CFP or review storage and is idempotent by event/proposal provenance. `GET /api/events/{eventId}/content` returns an organizer-wide or person-scoped speaker workspace. Organizer-only commands manage session fields/readiness, request speaker work, record communication, and explicitly approve assets for publication. Speaker-only completion, profile, and upload mutations enforce the event/person boundary before writes; every speaker upload begins private regardless of caller input. A profile or session edit and the attributed revision recording the state it replaced are one D1 batch, and a restore takes the same path, so neither half can outlive the other: a canonical write a constraint refuses leaves behind no revision claiming an edit that never happened. Both statements carry the same guard — this row, still exactly as it was read — which makes the pair a compare-and-swap and collapses three different losses into one answer of "nothing happened, look again": the row was deleted after the read, so a zero-row `UPDATE` cannot be mistaken for a write that landed; the row was changed by a writer that records no revision, such as a speaker choosing a headshot, which the edit must not revert by putting every column back the way it read them; or the row was changed by another revised edit, which also took the next revision number and so trips `UNIQUE(entity_type, entity_id, revision_number)`. Revision numbers are therefore allocated by the write rather than reserved by the caller, which is what stops a valid edit being refused for arriving at the same moment as another. Each loss is retried against a re-read row, so both organizers editing one speaker keep attributed history and the later edit lands on top of the earlier instead of reverting it from a stale copy, and each snapshot is the state the row actually held when the revision was written rather than one the caller read earlier. A row that has genuinely gone answers as absent, and a driver that cannot say how many rows it touched is an error rather than another retry, because a write that already landed must not be attempted twice. A revision is stamped when the actor asked but never earlier than the revision it follows, so a retried edit cannot land above the edit it lost to in a history listed by time. Losing five times running is reported as `409 CONFLICT`: contention to retry, not a malformed request, and the four content routes that can raise it declare it. Every other writer of these rows is narrowed for the same reason: choosing or clearing a headshot writes that column, a CSV import writes the workflow, logistics and custom fields it owns, and neither carries back the rest of a row as it stood when they read it — a picture is not a licence to rewrite a bio. `PUT /api/speaker-profiles/{profileId}/photo` names one of that profile's own image uploads as its headshot and `DELETE` on the same address clears it; the owning speaker or an organizer of that event may call either and nobody else may, and an asset that belongs to another profile or is not an `image/*` upload is refused `400 VALIDATION_FAILED` with `fieldErrors.assetId`. Naming a headshot never changes the asset's visibility — publication stays an organizer decision — and deleting the asset clears the profile column that pointed at it, so no snapshot can advertise a URL the asset route would refuse. R2 stores canonical asset bytes while public visibility remains organizer-controlled. Publication is reversible: `POST /api/speaker-assets/{assetId}/unpublish` returns an asset to private, `DELETE /api/speaker-assets/{assetId}` removes the row and the stored object for the uploading speaker or an event organizer, and `GET /api/speaker-assets/{assetId}` serves bytes anonymously only while the asset is publishable *and* its event is published, so unpublishing an event withdraws what its public page exposed. A withheld, withdrawn, deleted, or nonexistent asset are one indistinguishable 404. `DELETE /api/content-sessions/{sessionId}` withdraws a session from the programme: organizer-only, it removes the session and drops every agenda placement holding it through the agenda's public application interface, so the board cannot keep a slot for a session that no longer exists, and it answers the refreshed workspace. It is the reversal path for an abstract that was accepted and later declined; the speaker profile, its tasks, and its uploads are untouched, and the session leaves the public page at the next publish because published snapshots are immutable. Agenda, publishing, CRM, and communications consumers use separate least-privilege application projections rather than the private workspace. Every session the workspace returns carries `schedule` only when the event's *published agenda* places it — resolved through `ContentAgendaInterface` on each read, never stored on the session — so the organizer's Schedule column, the speaker portal, and the `.ics` export always agree with the agenda publication in force; a session the published agenda does not place has no `schedule` key at all. That is the agenda publication, not the site publication, and the difference is load-bearing: `GET /api/public/events/{slug}/schedule` and the event hub serve the projection frozen at the last *site* publish, so republishing the agenda alone moves the portal, the Schedule column, and the `.ics` while the public programme stays where it was until the organizer publishes the site as well, exactly as `PRD-PUB-001` states for every other source. The two reconverge at that publish; nothing may assume they are the same bytes in between. `GET /api/events/{eventId}/speaker-calendar.ics` derives deterministic calendar bytes from those same published placements, omits any session the agenda does not place, answers `404 NOT_FOUND` when that leaves no component, and normalizes all newline forms before escaping text.

CRM routes come in two scopes, and the addressing is the boundary rather than a convention on top of it. The event pipeline stays under `/api/events/{eventId}/prospects*`, requires event-scoped `crm:manage`, and is unchanged. The organization-wide speaker directory is addressed by organization instead — `/api/organizations/{organizationId}/crm/{contacts,duplicates,merges,segments,imports,outreach,dashboard}` — because an event-scoped path could not carry an answer that spans events, and because addressing it by organization means cross-event visibility has exactly one place to be authorized. That authorization takes three conditions together: `crm:manage`, membership of the named organization, and that the capability was earned on an event *belonging to* that organization; the third is what stops a grant from one organization reading another's directory when the actor belongs to both. Two directory routes write against a named event — `POST /api/organizations/{organizationId}/crm/contacts/{contactId}/events`, which sources a contact into that event's pipeline, and `POST /api/organizations/{organizationId}/crm/outreach`, whose deliveries communications records against it. Both make the same two additional checks, as does `POST /api/organizations/{organizationId}/crm/outreach/preview`, which names an event and writes nothing: the event-scoped `crm:manage` — a plain capability denial when it fails — and that the event belongs to the organization, refused `403 FORBIDDEN` "That event is not part of this organization." The push route creates or reuses that event's prospect and then runs the same idempotent conversion command the pipeline uses, so sourcing a contact twice yields one prospect and one speaker. `imports/preview` and `outreach/preview` write nothing, and both resolve what the commit would do rather than approximating it: the import preview classifies every row against the live directory using the same code the commit runs, including the capacity rule, and the outreach preview resolves the template through communications' `prepareEnqueue`, so an unknown template key is refused on the screen showing what will be sent. Each preview is also what the following command acts on — the import commits the bytes it described and the send targets the command it resolved — because both inputs stay editable while the result is on screen. A file past the CRM's import row limit is refused whole rather than started, since every row costs a read to classify and a statement to commit. A second live contact on one address is refused `409 CONFLICT` with `fieldErrors.email` naming the merge, which is also what the partial unique index on `(organization_id, email)` enforces underneath. Merging names its primary explicitly and deletes nothing: the losing rows survive behind `merged_into_id` and their addresses stay searchable as aliases.

POST /api/auth/code returns the same response and sends the same fixed-content mail whether or not
an address is registered; POST /api/auth/verify establishes a production signed cookie only for a
linked identity. POST /api/auth/tokens mints a bearer identity reduced to
one authorized event. Organization API clients use the distinct
`Authorization: Bearer grn_<prefix>.<secret>` grammar and are administered at
`/api/organizations/{organizationId}/api-clients`. Create, list, rotate, and revoke require a
real organizer session; listing never returns a secret or digest. Creation and rotation return
the plaintext once, rotation accepts the previous credential for 24 hours, and revocation is
observed on the next request. A client resolves to exactly its owning organization and the
intersection of its declared capability/event grants with its creator's current access. Tenant
identity does not widen event reads beyond the allowlist; the organization-level `events:create`
scope grants the resulting organizer role to the human who created the client.
GET /api/auth/config reports which doors this deployment actually offers —
`demoMode` and `google` — so a sign-in surface renders what can complete rather than what exists in
the codebase. GET /api/auth/google/start is a plain 302 to Google rather than a JSON endpoint the
client follows, so the button is an ordinary link with no script and no preflight; it sets a
short-lived `Lax` cookie carrying the attempt id, is throttled per client address alone, and
answers 404 where Google is unconfigured. GET /api/auth/google/callback spends that attempt exactly
once, verifies the `id_token` before reading any claim, links or provisions the identity, sets the
same signed session cookie the emailed-code path sets, and redirects to `/` — or `/?welcome=1` when
this sign-in created the account. Every refusal it can make lands on `/signin?auth=failed` with the
reason in the log: an unknown attempt, a mismatched `state`, an expired attempt, a signature that
does not verify and an unverified address are one indistinguishable outcome, because naming which
check refused is the oracle the flow exists to deny. Both redirect targets are string literals.
POST /api/auth/signout revokes this browser's session and then clears its cookie, answering
`{ "signedOut": true }` whether or not a session was present. It is revocation now: the cookie
carries the id of a row in `identity_sessions`, every authenticated request refuses a credential
whose row is missing, revoked or expired, and an event-scoped bearer token carries its parent
session's id and dies with it. The response still names the field `signedOut` — a shape deployed
clients already read — and still reports no count, because a count would tell an unauthenticated
caller whether the cookie it presented was real. POST /api/auth/sessions/revoke-all ends every live
session of the authenticated user and answers `{ "revoked": <count> }`, which is safe to report
because the route requires `authentication === "session"` first: a demo persona cookie resolves as
`demo` and is refused, and a deployment that records no sessions answers 404. A session token
minted before session records existed carries no session id and is refused outright, so the change
signs everybody out once.

Membership administration is addressed by organization, for the same reason the CRM directory is:
the answer spans events, so an event-scoped path could not carry it, and the organization is the
one place cross-event visibility is authorized. `GET /api/organizations/{organizationId}/members`
returns the members and every invitation; `POST .../invitations` creates one and answers its token
**once**, because only a SHA-256 digest is stored and nothing can reissue it; `DELETE
.../invitations/{invitationId}` withdraws one; `DELETE .../members/{userId}` removes somebody from
the organization and from every role on its events; `PUT` and `DELETE` on
`.../events/{eventId}/roles/{userId}` grant and revoke one role on one event, addressed under the
owning organization because that is where the authorization runs; and
`GET .../audit-events` serves that organization's own identity audit log. Authorization takes the
same three conditions as the CRM directory — `identity:manage`, membership of the named
organization, and that the capability was earned on an event belonging to it — on a new
event-earned capability rather than a global administrator role. `POST /api/invitations/accept` is
addressed outside any organization, because the caller does not belong to one yet; it requires
`authentication === "session"` and grants to *that* identity, never to the address the invitation
names, so a demo persona can never accept one. An unknown, expired, revoked or already-accepted
token are one indistinguishable 404. Removing a membership or a role takes effect on the next
request without revoking any session, because the actor is re-derived from D1 every time.
GET /api/session returns the freshly resolved actor, memberships, event roles,
and capabilities. /api/demo-session remains an internal harness route available only with
DEMO_MODE=true and exact ENVIRONMENT=development. Errors follow
[`ARC-ERR-001`](../architecture/error-observability.md).

`GET /api/events/assigned` returns event metadata assigned to the signed-in identity — including the public demo identity, which holds no `events:read` — allowing direct login and reload without retained private workspace state. It requires a session and answers 401 without one, which is why it does not live under `/api/public`: nothing in that namespace may demand a session. Every route under `/api/public/*` answers CORS preflight with 204 and `Access-Control-Allow-Origin: *`, serves 200 responses with `Cache-Control: public, no-cache` plus an ETag, and marks everything else `no-store`; anonymous asset bytes carry the same policy with their own upload-derived validator, while the private copy stays `private, no-store`. The policy is deliberately validator-based rather than time-based: every read revalidates, an unchanged representation returns a bodyless 304 that still carries `Access-Control-Allow-Origin` and the correlation id, and closing a CFP, reopening it, unpublishing an event, or returning an asset to private is visible on the next read instead of after a freshness window. `POST /api/public/events/{eventId}/submissions` is throttled per client address and answers `RATE_LIMITED` with `Retry-After` beyond the window; the counter is per isolate and therefore best effort. The key deliberately excludes the event id: it arrives in the path and is never checked for existence, so including it let one caller mint unlimited counters and, against the bounded key table, evict its own exhausted one. Organizer-scoped CFP routes expose the editable form at `GET/PUT /api/events/{eventId}/cfp` and explicit `publish`, `close`, and `reopen` transitions at `POST /api/events/{eventId}/cfp/state`. They require the actor's organizer role for that exact event before parsing mutation bodies. The three transitions are independent: `publish` replaces the form applicants see and carries the live open/closed state over unchanged — republishing a closed call leaves it closed and submissions keep answering `CFP_UNAVAILABLE` — while `close` and `reopen` are the only transitions that change it. Only a first publication, which has no live state to preserve, opens the call. `GET /api/public/events/{eventId}/cfp` returns only the last explicitly published snapshot, including its open/closed state; saving a replacement draft does not withdraw that snapshot. `POST /api/public/events/{eventId}/submissions` validates answers against the published field configuration and atomically inserts only while that exact published version remains open. It uses an event-scoped idempotency key to return one durable confirmation across retries. Duplicate field IDs and select fields without options are rejected by the shared schema, which also bounds a submission to at most 40 answers of at most 10,000 characters each; each answer is then held to the `maxLength` its published field advertises, defaulting per field type.

CFP draft `PUT` requests carry the `expectedVersion` returned by the organizer `GET`. The repository advances that editable revision with one atomic compare-and-swap; a stale editor receives `409 CONFLICT`, the winning draft stays unchanged, and the composer offers an explicit reload. This precondition applies only to editable drafts: published snapshot transitions and idempotent proposal submission retain their existing independent concurrency guards.

Event-template routes are addressed two ways, because a template and an application of one are different things. The library is organization-scoped — `GET`/`POST /api/organizations/{organizationId}/event-templates`, then `GET`/`PATCH /api/event-templates/{templateId}` and `POST` on its `/versions` and `/duplications` — and a template belonging to another organization answers byte-identically to an id that names nothing, correlation id aside, because distinguishing them would turn the route into an oracle for what an organization owns. Applying is addressed by the **destination event**: `POST /api/events/{eventId}/template-application-previews` writes nothing and returns the per-category breakdown, and `POST /api/events/{eventId}/template-applications` performs it. That is two requests rather than one for a reason `ARC-FLOW-006` records in full: the request actor is resolved once in middleware, so a single call that created the destination event and then configured it would be denied by every capability check on the event it had just made. Both bodies name an explicit `version` — never "latest", which would make the same request produce a different event next week — and a required `destination` range, because an event carries no dates of its own and every absolute time in the payload is remapped onto that range in the destination's timezone. The apply response is `200` rather than `201`: applying the same version again is a supported, converging operation, so a status meaning "a new thing now exists" would be wrong on the second call. It reports one line per category — `applied`, `skipped`, `incompatible`, `unauthorized` or `failed` with a reason — and does **not** promise atomicity across domains: a failed category leaves the succeeded ones in place, the envelope says `partial`, and re-applying is the repair. Speaker task checklists are authored through content's own routes — `GET`/`POST /api/events/{eventId}/speaker-task-templates` and `POST /api/events/{eventId}/speaker-checklist-assignments`. The save is `POST` rather than `PUT` because it upserts and never deletes: a line the request does not name survives, and `PUT` would promise a replacement it does not perform. The assignment command answers only the tasks it created, so calling it a second time legitimately returns none.
`GET /api/events/{eventId}/search` is platform's permission-aware read across the whole event, and its response shape is the specification rather than a convenience. It takes `q` (at least two characters, at most 120) and an optional `limit` (1–25, default 10) capping each section, and answers five sections — content, review, agenda, communications, crm — each in one of three states. `ok` carries its results; `unauthorized` means the caller's role does not include that source; `failed` carries the standard error envelope with this request's correlation id. The three-state union is deliberately *not* the two-state `{ ok }` union `GET /api/events/{eventId}/overview` uses. Overview is organizer-only, so a capability refusal there fails the whole request; search is reached by organizers, reviewers and speakers alike, so a refusal is an ordinary fact about the caller and must not be reported as an outage — a reviewer searching an event legitimately reads two of the five. Only the request itself is authorized centrally, on `events:read` for the named event; each section is then composed through the owning domain's own public application interface under that domain's capability, so nothing here can return a record the caller could not already open. There is no index and no projection storage. Every result carries an `href`: the console path plus `?event=`, produced by the server because which surface a record opens depends on the role that read it — a reviewer's proposal belongs to `/reviews` and an organizer's to `/abstracts`. A section that fails is logged once, server-side; a section that is `unauthorized` is not logged at all, because that is the authorization model working. A query below the minimum is `400 VALIDATION_FAILED` with `fieldErrors.q`, and an out-of-range `limit` the same with `fieldErrors.limit`.

`GET /api/events/{eventId}/inbox` is the same composition read for a different question: what is waiting. It answers five categories — `programme`, `speakerWork`, `reviews`, `deliveries`, `publication` — in the same three states, under the same per-source rule, and carries a `derivedAt` because every relative label the surface renders is measured from the moment the answer was composed rather than from the browser's clock. Every item is derived on the read; **nothing marks one done**, so the way to remove an item is to resolve the condition it names. The `reviews` category, like search's proposal section, is chosen by role: an organizer sees every outstanding assignment and who holds it, a reviewer sees their own from the masked queue, and the organizer projection is never reached for a reviewer. `POST /api/events/{eventId}/inbox/dismissals` records that the signed-in actor has seen an occurrence and is not acting on it; the body's `itemKey` is checked against the inbox that actor can derive right now, so an item that has already resolved, one belonging to another event, and one in a category their role cannot read are all `404 NOT_FOUND` rather than a stored row. `DELETE /api/events/{eventId}/inbox/dismissals/{itemKey}` undoes it and is idempotent — a key that is not dismissed answers `204` as well, because the caller asked for it to be gone and it is gone. A dismissal is per actor and its key carries the occurrence rather than the record, so a re-derived identical item stays dismissed while a moved deadline or a further failed attempt comes back. Programme items are no longer the exception (issue #180): the agenda draft carries `occurrences` — the board revision at which each session's placements last changed, and at which each time slot was last retimed — and each conflict carries the later of its two placements' numbers and its two slots' as `occurrence`, so an unplaced session's key is `agenda-unplaced:{sessionId}:{occurrence}` and a conflict's is `agenda-conflict:{kind}:{placementId}:{conflictingPlacementId}:{occurrence}`. A session placed and taken off the board again, and a clash resolved and reintroduced between the same two placements, both return open; a dismissal survives every edit to a different session, which is why the number is per session rather than the board revision. A dismissal recorded before the numbers existed reads as occurrence zero and its item returns open once, which is the safe direction of that one-time change.

`GET /api/events/{eventId}/audit` is the unified audit timeline: one event, newest first, `limit` (1–50, default 25) and an opaque `cursor`, gated on `events:settings:read` rather than `events:read` because the log names who did what. The cursor is `(occurredAt, id)` and the id is in it deliberately — a publication and its announcement are written in the same millisecond, and a cursor on the timestamp alone would repeat one of them or skip it. Each record carries `occurredAt`, `actorId` (null when nobody signed it), `actorName`, `source` (`human | api | agent | system`; only the first and last are produced today), `action`, `targetType`, `targetId` and `correlationId`. The idempotency key is **not** in the response: it is derived from the fact and is the one field a caller could use to guess at records they were not shown. Storage is append-only through two triggers that refuse an `UPDATE` and a `DELETE`, and `UNIQUE(organization_id, idempotency_key)` is what makes a replayed command produce one record. Writers come in two shapes, mirroring communications' `enqueue`/`prepareEnqueue`: `record(...)` writes and never throws, and `prepare(...)` returns a record the caller commits inside its own batch — which is how a published schedule and the record of who published it survive or fail together. Five domains are observed, each through a port it declares itself: content's `SpeakerNotificationPort`, review's `ReviewNotificationPort`, publishing's `PublicationNotificationPort`, the agenda's publication batch, and the delivery communications enqueues. No domain imports platform to be recorded; the composition root binds each port, which is why adding the timeline changed no domain's own logic.

## Domain events

- `EVT-SUBMISSION-RECEIVED`
- `EVT-REVIEW-COMPLETED`
- `EVT-CONTENT-ACCEPTED`
- `EVT-SPEAKER-CONVERTED`
- `EVT-SCHEDULE-PUBLISHED`
- `EVT-PROJECTION-REQUESTED`

Events are versioned facts with organization/event scope, event ID, occurrence time, correlation ID, and causation ID. Consumers are idempotent. They coordinate domains; they are not an untyped dumping ground.

Provider ports and semantics are defined in [integrations](../architecture/integrations.md). Generated OpenAPI is linked above and checked for drift in CI.

## Communications and integration routes

- `POST /api/communications/templates` creates an immutable, organization-scoped template version.
- `GET /api/communications/templates?organizationId={organizationId}` returns every version of every template, grouped by key and newest version first within each key. Versions are immutable, so correcting a message publishes the next version of the same key and the earlier one stays readable — a delivery names the version it used.
- `GET /api/communications/recipients?organizationId={organizationId}&eventId={eventId}` returns the event's speakers and the address each can be reached at, resolved through identity-access rather than by reading `event_roles` or content's speaker profiles. A speaker with no linked identity email is listed with a null address rather than omitted.
- `POST /api/communications/broadcasts` sends one template version to every reachable speaker on the event and answers `202` with the number queued, the speakers it could not reach, and the deliveries themselves. Each speaker gets their own delivery, their own rendered message and their own retry. The idempotency key is `broadcast:{templateKey}:v{version}:{eventId}:{userId}`, so a repeated send converges on one delivery per speaker while a *new version* of the same template does send again — that is the intended way to correct a message that went out wrong.
- `POST /api/communications/deliveries` accepts a typed trigger and stable idempotency key, returning the existing delivery for a duplicate key.
- `GET /api/communications/history?organizationId={organizationId}&eventId={eventId}&limit={limit}&cursor={cursor}` returns at most 50 deliveries with ordered immutable attempts and an optional `nextCursor`; persistence loads each page and its attempts in two bounded queries.
- `POST /api/communications/deliveries/{deliveryId}/retry?organizationId={organizationId}` explicitly requeues a retrying or terminal delivery without removing history.

All seven routes require `communications:manage` and enforce the owning organization. Email deliveries require a known template key/version, and the message is rendered from that version against the delivery's payload at enqueue: the delivery stores the exact subject and body that were sent, so a retry re-sends the text that was composed rather than whatever the template says by then, and an unfilled `{{placeholder}}` refuses the enqueue with `400 VALIDATION_FAILED` naming the placeholder rather than mailing half a sentence. Airtable and Accelevents deliveries require a positive projection version and are outbound-only; SQL remains canonical. The runtime schemas in `@greenroom/contracts` own validation for these request shapes.

Missing template/delivery references return `404 NOT_FOUND`; invalid template/channel semantics return `400 VALIDATION_FAILED`; and recovery races or non-recoverable states return `409 CONFLICT`.
