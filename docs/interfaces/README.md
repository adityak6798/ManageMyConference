# Interface catalog

Status: canonical | Owner: architecture | Last verified: 2026-08-11

Shared Zod schemas own every current request and response shape: event mutations/lists/basic metadata, agenda draft/placement/publication/public projection, current session/capabilities, demo session, health, and the standard error envelope. They generate [`packages/contracts/openapi.json`](../../packages/contracts/openapi.json), and CI rejects drift. The OpenAPI document covers health, the internal demo-cookie route, session, event, agenda, and public-schedule routes, cookie security, and implemented success/error statuses. Domain types own business semantics. Drizzle declares intended storage, immutable SQL migrations own deployed history, and the D1 adapter owns persistence behavior. Explicit tested mappers connect transport, domain, and storage models.

## Route groups

- `API-AUTH-*`: session, seeded demo identity switch, current capabilities.
- `API-ORG-*`, `API-EVENT-*`: organization/event commands and queries.
- `API-CFP-*`, `API-REVIEW-*`: forms, submissions, assignments, evaluations.
- `API-CONTENT-*`, `API-CRM-*`: speakers, sessions, tasks/assets, prospects/activity/conversion.
- `API-AGENDA-*`: rooms, tracks, placements, conflicts.
- `API-COMMS-*`, `API-INTEGRATION-*`: templates, outbox, attempts, projection state.
- `API-PUBLIC-*`: published hub, schedule, sessions, speakers, and CFP/embed reads.

Implemented review routes are `GET /api/events/{eventId}/review/organizer`, `PUT /api/events/{eventId}/review/statuses`, `PUT /api/events/{eventId}/review/plan`, `POST /api/events/{eventId}/review/assignments`, `POST /api/events/{eventId}/review/transitions`, `POST /api/events/{eventId}/review/decisions`, `GET /api/events/{eventId}/review/assignments`, `DELETE /api/events/{eventId}/review/assignments/{assignmentId}`, `POST /api/events/{eventId}/review/assignments/{assignmentId}/conflict`, and `PUT /api/events/{eventId}/review/assignments/{assignmentId}/evaluation`. The transitions endpoint has an all-or-nothing atomic contract and refuses the two reserved decision statuses outright, naming the decisions endpoint: reaching `accepted`/`declined` is the effect of a recorded decision, and a transition into one wrote a status with no decision behind it. The statuses endpoint completes rather than refuses a set that omits the reserved decision statuses, and every status the organizer projection advertises is stored, so anything it offers is reachable — the pipeline steps by a transition, the two reserved outcomes by a decision. Removing an assignment is `DELETE` on the assignment: it takes any draft evaluation and declared conflict with it, releases the rubric lock that the existence of an assignment holds, and is refused once that reviewer has completed an evaluation whose score is already counted in the aggregate. The decisions endpoint records the accept/decline decision and, for an accepted outcome, composes the content acceptance in the same request; the two are not one transaction, so each proposal's `acceptances` entry reports `content` with its session id or `decision_only` with the content domain's own field errors. A `decision_only` outcome leaves the decision durable and is repaired by posting the identical decision again. Reviewer assignment validates the named user's event reviewer role. Evaluation completion is terminal, retry-repairable, and atomically writes the evaluation, aggregate, and unique versioned completion event. The reviewer assignment response deliberately omits aggregate outcomes. Shared Zod schemas define every body and response and generate the OpenAPI artifact.

Agenda draft routes are scoped below `/api/events/{eventId}/agenda` and require `agenda:manage` plus either an event organizer role or organizer membership in the event's owning organization. Resource `PUT` initializes or replaces rooms, tracks, and slots while rejecting deletion of an in-use resource. Placement `PUT` is idempotent by placement ID and uses optimistic revision retries to preserve concurrent edits; `DELETE` removes a placement with the same protection. `POST /publications` rejects conflicts with `AGENDA_CONFLICT` and resource-specific explanations. `GET /api/public/events/{slug}/schedule` requires no session and returns the latest immutable publication's `version` and `publishedAt` — never its audit-only actor identity — together with the sessions the event's published projection places, each under the public slug that projection assigned and carrying its title, abstract, format, track, speaker slugs, room, and start/end instants. The agenda snapshot itself is not serialized: it covers the organizer's whole board, including sessions whose content is still a draft, and is keyed by storage identifiers, so nothing but the publication's identity crosses that boundary. A published session with no placement is not on the schedule; it remains on the event hub. The placement detail is the projection's own copy, so the schedule and the hub always agree about a session; republishing the agenda advances `version` before that detail follows, exactly as every other source moves ahead of the snapshot until the site is published again. The route is addressed by the event's public slug and gated on the publication being live: an unknown slug, an unpublished event, and an event whose agenda was never published all return the same `NOT_FOUND` "This event is not published." envelope, so unpublishing retracts the schedule along with the rest of the public surface. A durable `EVT-SCHEDULE-PUBLISHED` v1 outbox emission remains follow-up work before downstream consumers rely on it.

Migration `0002_identity_event_foundation.sql` preserves pre-foundation events under a stable imported organization and assigns the seeded organizer membership/event roles before adding organization scope. Deterministic reset replaces that imported state with the role-complete local fixture.
Content routes are defined by the generated OpenAPI contract. `POST /api/events/{eventId}/content/accept` atomically consumes a proposal/review outcome without reading CFP or review storage and is idempotent by event/proposal provenance. `GET /api/events/{eventId}/content` returns an organizer-wide or person-scoped speaker workspace. Organizer-only commands manage session fields/readiness, request speaker work, record communication, and explicitly approve assets for publication. Speaker-only completion, profile, and upload mutations enforce the event/person boundary before writes; every speaker upload begins private regardless of caller input. `PUT /api/speaker-profiles/{profileId}/photo` names one of that profile's own image uploads as its headshot and `DELETE` on the same address clears it; the owning speaker or an organizer of that event may call either and nobody else may, and an asset that belongs to another profile or is not an `image/*` upload is refused `400 VALIDATION_FAILED` with `fieldErrors.assetId`. Naming a headshot never changes the asset's visibility — publication stays an organizer decision — and deleting the asset clears the profile column that pointed at it, so no snapshot can advertise a URL the asset route would refuse. R2 stores canonical asset bytes while public visibility remains organizer-controlled. Publication is reversible: `POST /api/speaker-assets/{assetId}/unpublish` returns an asset to private, `DELETE /api/speaker-assets/{assetId}` removes the row and the stored object for the uploading speaker or an event organizer, and `GET /api/speaker-assets/{assetId}` serves bytes anonymously only while the asset is publishable *and* its event is published, so unpublishing an event withdraws what its public page exposed. A withheld, withdrawn, deleted, or nonexistent asset are one indistinguishable 404. `DELETE /api/content-sessions/{sessionId}` withdraws a session from the programme: organizer-only, it removes the session and drops every agenda placement holding it through the agenda's public application interface, so the board cannot keep a slot for a session that no longer exists, and it answers the refreshed workspace. It is the reversal path for an abstract that was accepted and later declined; the speaker profile, its tasks, and its uploads are untouched, and the session leaves the public page at the next publish because published snapshots are immutable. Agenda, publishing, CRM, and communications consumers use separate least-privilege application projections rather than the private workspace. Every session the workspace returns carries `schedule` only when the event's *published agenda* places it — resolved through `ContentAgendaInterface` on each read, never stored on the session — so the organizer's Schedule column, the speaker portal, and the `.ics` export always agree with the agenda publication in force; a session the published agenda does not place has no `schedule` key at all. That is the agenda publication, not the site publication, and the difference is load-bearing: `GET /api/public/events/{slug}/schedule` and the event hub serve the projection frozen at the last *site* publish, so republishing the agenda alone moves the portal, the Schedule column, and the `.ics` while the public programme stays where it was until the organizer publishes the site as well, exactly as `PRD-PUB-001` states for every other source. The two reconverge at that publish; nothing may assume they are the same bytes in between. `GET /api/events/{eventId}/speaker-calendar.ics` derives deterministic calendar bytes from those same published placements, omits any session the agenda does not place, answers `404 NOT_FOUND` when that leaves no component, and normalizes all newline forms before escaping text.

CRM routes come in two scopes, and the addressing is the boundary rather than a convention on top of it. The event pipeline stays under `/api/events/{eventId}/prospects*`, requires event-scoped `crm:manage`, and is unchanged. The organization-wide speaker directory is addressed by organization instead — `/api/organizations/{organizationId}/crm/{contacts,duplicates,merges,segments,imports,outreach,dashboard}` — because an event-scoped path could not carry an answer that spans events, and because addressing it by organization means cross-event visibility has exactly one place to be authorized. That authorization takes three conditions together: `crm:manage`, membership of the named organization, and that the capability was earned on an event *belonging to* that organization; the third is what stops a grant from one organization reading another's directory when the actor belongs to both. Two directory routes write against a named event — `POST /api/organizations/{organizationId}/crm/contacts/{contactId}/events`, which sources a contact into that event's pipeline, and `POST /api/organizations/{organizationId}/crm/outreach`, whose deliveries communications records against it. Both make the same two additional checks, as does `POST /api/organizations/{organizationId}/crm/outreach/preview`, which names an event and writes nothing: the event-scoped `crm:manage` — a plain capability denial when it fails — and that the event belongs to the organization, refused `403 FORBIDDEN` "That event is not part of this organization." The push route creates or reuses that event's prospect and then runs the same idempotent conversion command the pipeline uses, so sourcing a contact twice yields one prospect and one speaker. `imports/preview` and `outreach/preview` write nothing; the import preview classifies every row against the live directory using the same code the commit runs, while the outreach preview resolves recipients and authorization only, because the delivery entry point available to it writes and a preview bound to it would queue the messages it claims to be previewing. A second live contact on one address is refused `409 CONFLICT` with `fieldErrors.email` naming the merge, which is also what the partial unique index on `(organization_id, email)` enforces underneath. Merging names its primary explicitly and deletes nothing: the losing rows survive behind `merged_into_id` and their addresses stay searchable as aliases.

POST /api/auth/code returns the same response and sends the same fixed-content mail whether or not
an address is registered; POST /api/auth/verify establishes a production signed cookie only for a
linked identity. POST /api/auth/tokens mints a bearer identity reduced to
one authorized event. GET /api/session returns the freshly resolved actor, memberships, event roles,
and capabilities. /api/demo-session remains an internal harness route available only with
DEMO_MODE=true and exact ENVIRONMENT=development. Errors follow
[`ARC-ERR-001`](../architecture/error-observability.md).

`GET /api/events/assigned` returns event metadata assigned to the signed-in identity — including the public demo identity, which holds no `events:read` — allowing direct login and reload without retained private workspace state. It requires a session and answers 401 without one, which is why it does not live under `/api/public`: nothing in that namespace may demand a session. Every route under `/api/public/*` answers CORS preflight with 204 and `Access-Control-Allow-Origin: *`, serves 200 responses with `Cache-Control: public, no-cache` plus an ETag, and marks everything else `no-store`; anonymous asset bytes carry the same policy with their own upload-derived validator, while the private copy stays `private, no-store`. The policy is deliberately validator-based rather than time-based: every read revalidates, an unchanged representation returns a bodyless 304 that still carries `Access-Control-Allow-Origin` and the correlation id, and closing a CFP, reopening it, unpublishing an event, or returning an asset to private is visible on the next read instead of after a freshness window. `POST /api/public/events/{eventId}/submissions` is throttled per client address and answers `RATE_LIMITED` with `Retry-After` beyond the window; the counter is per isolate and therefore best effort. The key deliberately excludes the event id: it arrives in the path and is never checked for existence, so including it let one caller mint unlimited counters and, against the bounded key table, evict its own exhausted one. Organizer-scoped CFP routes expose the editable form at `GET/PUT /api/events/{eventId}/cfp` and explicit `publish`, `close`, and `reopen` transitions at `POST /api/events/{eventId}/cfp/state`. They require the actor's organizer role for that exact event before parsing mutation bodies. The three transitions are independent: `publish` replaces the form applicants see and carries the live open/closed state over unchanged — republishing a closed call leaves it closed and submissions keep answering `CFP_UNAVAILABLE` — while `close` and `reopen` are the only transitions that change it. Only a first publication, which has no live state to preserve, opens the call. `GET /api/public/events/{eventId}/cfp` returns only the last explicitly published snapshot, including its open/closed state; saving a replacement draft does not withdraw that snapshot. `POST /api/public/events/{eventId}/submissions` validates answers against the published field configuration and atomically inserts only while that exact published version remains open. It uses an event-scoped idempotency key to return one durable confirmation across retries. Duplicate field IDs and select fields without options are rejected by the shared schema, which also bounds a submission to at most 40 answers of at most 10,000 characters each; each answer is then held to the `maxLength` its published field advertises, defaulting per field type.

Migration `0002_identity_event_foundation.sql` preserves pre-foundation events under a stable imported organization and assigns the seeded organizer membership/event roles before adding organization scope. Deterministic reset replaces that imported state with the role-complete local fixture. Migrations `0003_cfp.sql`, `0004_cfp_published_snapshot.sql`, and `0005_cfp_snapshot_status.sql` add CFP-owned forms/submissions, preserve an independently readable published snapshot while organizers edit a later draft, and expose its state separately to the composer. The deterministic seed includes an open typed CFP.

Migration `0006_review_workflow.sql` extends CFP-owned submissions with triage status and an immutable typed-field snapshot, adds configured statuses/status audit, and introduces review-owned plans, assignments, conflicts, evaluations, outcomes, and completion-event records. Migrations `0007_review_completion_conflict_guard.sql` and `0008_review_conflict_completion_guard.sql` enforce conflict/completion mutual exclusion under concurrent requests. Migrations `0009_review_assignment_requires_plan.sql` and `0010_review_plan_lock.sql` atomically require a plan before assignment and lock rubric changes after assignment. Migrations `0011_cfp_transition_status_guard.sql`, `0012_cfp_status_in_use_guard.sql`, and `0013_cfp_submission_default_status.sql` atomically keep proposal transitions, configured-status edits, and new submissions consistent. Review reads non-email typed answers through the CFP submitted-proposal application interface and resolves organization scope through the events application service. The deterministic reset includes the shared CFP/review submission records, organizer triage, multi-role capability, and reviewer assignment perspectives.

Migration `0014_content_speaker_portal.sql` follows the CFP/review history and adds content-owned sessions, event-scoped speaker profiles, tasks, private asset metadata, and communication records. The review completion event remains an individual evaluation fact, not an acceptance decision; the stored `review_decisions` record is what authorizes content, and the content-acceptance command names only the proposal — title, abstract, format, and speaker identity are resolved through the review domain's public application interface and the speaker conversion port rather than supplied by the caller.

## Domain events

- `EVT-SUBMISSION-RECEIVED`
- `EVT-REVIEW-COMPLETED`
- `EVT-CONTENT-ACCEPTED`
- `EVT-SPEAKER-CONVERTED`
- `EVT-SCHEDULE-PUBLISHED`
- `EVT-PROJECTION-REQUESTED`

Events are versioned facts with organization/event scope, event ID, occurrence time, correlation ID, and causation ID. Consumers are idempotent. They coordinate domains; they are not an untyped dumping ground.

Provider ports and semantics are defined in [integrations](../architecture/integrations.md). Generated OpenAPI is linked above and checked for drift in CI.

## Communications and integration routes

- `POST /api/communications/templates` creates an immutable, organization-scoped template version.
- `POST /api/communications/deliveries` accepts a typed trigger and stable idempotency key, returning the existing delivery for a duplicate key.
- `GET /api/communications/history?organizationId={organizationId}&eventId={eventId}&limit={limit}&cursor={cursor}` returns at most 50 deliveries with ordered immutable attempts and an optional `nextCursor`; persistence loads each page and its attempts in two bounded queries.
- `POST /api/communications/deliveries/{deliveryId}/retry?organizationId={organizationId}` explicitly requeues a retrying or terminal delivery without removing history.

All four routes require `communications:manage` and enforce the owning organization. Email deliveries require a known template key/version. Airtable and Accelevents deliveries require a positive projection version and are outbound-only; SQL remains canonical. The runtime schemas in `@greenroom/contracts` own validation for these request shapes.

Missing template/delivery references return `404 NOT_FOUND`; invalid template/channel semantics return `400 VALIDATION_FAILED`; and recovery races or non-recoverable states return `409 CONFLICT`.
