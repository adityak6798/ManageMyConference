# Testing strategy

Status: canonical | Owner: quality | IDs: `TST-001`–`TST-006` | Last verified: 2026-08-11 (working tree: commit `3630977`)

Measured on 2026-08-11: `npm run check` exits 0 (37 tool tests; 132 API tests in 17 files; 93 web
tests in 12 files; 20 D1 tests in 11 files; both builds), `npm run test:e2e` is 30 passing browser
tests, `npm run test:quality` is 3. All of it is local: **no hosted CI run exists for any commit on
this branch**, so nothing below may be cited as CI-verified. Layer boundaries matter when reading a
result — the jsdom suites stub `fetch`, so a `@acceptance` marker there proves rendering and never
the pipeline behind it.

- `TST-001` Current unit tests cover event creation through the repository port, mapping, expiring/tamper-resistant signed demo sessions, production demo rejection, authorization behavior, and deterministic inputs. Domain-specific transitions/conflict rules are added with their features.
- `TST-002` Planned: repository and provider contract suites run against every fake/live implementation available in that environment.
- `TST-003` API tests cover shared request/response validation, demo-mode gating, signed session handling, distinct unauthenticated/forbidden behavior, safe error contracts, tenant-scoped event reads, and structured request logs with unexpected faults logged once. Miniflare proves existing-event migration, the D1 repository against the migrated database, and that applying reset twice restores the exact seed. Command idempotency expands with product capabilities.

  Every D1 integration test builds its database through one harness,
  [`apps/api/test/support/seeded-d1.ts`](../../apps/api/test/support/seeded-d1.ts):
  `createMigratedDatabase()` gives each call its own Miniflare instance and database name,
  applies **every** migration the directory holds in canonical filename order, and optionally
  the same `seed/reset.sql` that `npm run reset` writes. Adding a migration therefore requires
  no edit to any test. Before it, each test carried a hand-written subset of migration
  filenames — the lists drifted, and the shared reset ended up referencing tables several
  fixtures did not have. Two tests keep an explicit older schema, and only because they exist
  to prove a migration preserves data written under the previous one; they say so with
  `through`/`from` rather than by omitting files. A failing statement names its migration and
  the statement itself, and the harness's own properties — canonical order, trigger execution,
  isolation between databases, and a seed that can be applied twice with an identical result —
  are asserted in
  [`d1-harness.integration.test.ts`](../../apps/api/test/d1-harness.integration.test.ts).
- `TST-004` Playwright proves the identity/event shell: seeded persona sign-in, multi-event switching, authorized creation, persistence across reload, role-aware navigation, and visible denied/error behavior. Future P0 journeys add their own tagged scenarios.
- `TST-005` Context checks cover canonical domain assignments, IDs, links, routing by journey/acceptance/plan/path/symbol, trust-labeled generated backlinks/index drift, table ownership, cross-domain allowlists, dependency layers, and metadata. Generated/reference-untrusted backlinks cannot satisfy canonical proof. The AST error checker enforces error handling; shared-Zod OpenAPI generation has an independent drift check; `npm run schema:check` builds one database from the migrations and another from the declared Drizzle schema and diffs their structural models, defending itself with mutation self-tests. What that diff deliberately leaves uncovered is recorded as `GAP-006`; `npm run gates:check` fails the build when the gate scripts and the CI workflow disagree.
- `TST-006` The fast Playwright quality project starts the Worker against a fresh reset and the production artifact in `apps/web/dist`; it never measures Vite. Axe's WCAG 2 A/AA and 2.1 A/AA rules audit every organizer destination, the reviewer and speaker shells, all seven public routes, and all four embeds. Explicit checks cover skip links, banner/main/footer landmarks, focus after client navigation, dead organizer destinations, and horizontal overflow at 390px across every organizer and public route. The 390px check measures two things, because measuring only the first certified a page whose primary action was off-screen: the document does not overflow, **and** no control inside `main` lies outside the viewport. The second half is scoped by an explicit exemption list naming the organizer routes that cannot pass it yet, where a five- or six-column `table.data` cannot fit 390px and its Actions column falls inside the `.table-wrap` scroller. It found that defect on three surfaces; `/abstracts` and `/sessions` have since been restacked into cards below 780px by one shared recipe (`review.css` and `content.css`), leaving `/communications` at 7 controls. The exemption is named in `lifecycle-demo.spec.ts` rather than achieved by weakening the assertion for all eleven routes, and an entry leaves the list when its surface restacks. The organizer axe sweep also expands every `details.tool-panel` before auditing, because a closed disclosure renders nothing and would otherwise narrow the audit to the dashboard while the row still claimed the destination was clean. The built public home page is bounded at DOMContentLoaded under 1.5 seconds, less than 300 KiB transferred, and fewer than 12 resource requests; the pre-budget local measurement was 55 ms, 166 KiB, and 5 requests. The evaluator subset runs in pull-request CI and the scheduled gardening workflow. The single-artifact proposal-to-publication scenario is shipped: `apps/web/e2e/lifecycle.spec.ts` files one uniquely-titled proposal through the public form and follows it through triage, reviewer assignment, scoring, acceptance into content, publication readiness, agenda placement, schedule publication, and site publication, then asserts that same title and its provisioned speaker on `/events/:slug/schedule`, `/events/:slug/speakers`, and both embeds — and hands the fixture back. Deployment-preview smoke and credential-gated live-provider contracts remain release follow-ups because no production environment or live provider is declared.
- The browser suite is re-runnable: measured on 2026-08-11 it passed 30/30 immediately after `npm run reset` and 30/30 again against the same already-running servers with no reset in between (issue #72). It is re-runnable, not trace-free: each run leaves rows it does not remove, recorded as `DEBT-007`. It is also not per-spec reproducible: the specs share one mutable fixture at `workers: 1`, their order is load-bearing, and outside CI Playwright reuses running servers and so skips the reset entirely, which is why the [scorecard](../quality/scorecard.md) names the suite rather than a command per row. Every spec either restores what it mutates (the seeded CFP is reopened, the seeded onboarding checklist is re-requested, agenda placements and resources are handed back, a renamed session is renamed back and republished) or scopes its assertions to rows the run itself created (`00-seed-state.spec.ts` runs first, immediately after a reset, so that the CFP republish in `cfp.spec.ts` cannot repair a seed defect before it is asserted). Two exceptions are inherent and documented in the specs that carry them: a completed evaluation and a declared conflict are terminal by design, so `review-workflow.spec.ts` files its own abstracts each run; and no product affordance returns a communication delivery to a failed state, so `communications.spec.ts` asserts the recovery when a failed delivery exists and the complementary refusal when one does not — which means the recovery half runs only on the first suite run after a reset, and every later run in the same fixture asserts the complement instead.

`ACC-REVIEW` is exercised by review-domain unit tests, HTTP role-negative and aggregate-bias tests, D1 migration/atomic-transition persistence tests, and an organizer-to-reviewer Playwright journey. Cross-event, unassigned reviewer, unauthorized role, score validation, and conflict paths fail closed.

What the suites do **not** cover, so that a green run is not read as more than it is: **no test exercises a real provider in either direction** (`GAP-010`, `GAP-012`) — lifecycle-triggered communications are covered as of issue #66, in `communications-lifecycle.test.ts` and the notification cases in `content-service.test.ts` and `review-service.test.ts`, and the inbound Accelevents registration sync is covered as of issue #58, but every send in the first goes to the deterministic fake and every read in the second comes from an in-repository roster with a stubbed `fetch`, so both prove our handling and neither proves a third party's API; no mail client has rendered a calendar invitation for the same reason; and every authorization negative is proved against development-only demo identities, because production authentication does not exist (`GAP-007`).

Acceptance tests declare their `ACC-*` identifier. Prefer public interfaces over implementation details. The browser suite uses deterministic local services and retains traces/screenshots/reports on CI failure. External provider suites will use deterministic fakes in PR CI. Flaky tests are fixed or quarantined with an owner and quality gap; blind retries are forbidden.
