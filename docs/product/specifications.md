# Bounded product specifications

Status: canonical | Owner: product | Last verified: 2026-08-14

## Events and access

- `PRD-EVT-001` One organization owns many events. Every event command names its organization or event scope, repositories constrain reads to the actor's organization memberships or event assignments, and event settings and records never leak across events. Organizers may create and switch among events in organizations they belong to, and an event-scoped organizer may rename an event or change its IANA timezone. Deliberately creating an additional event uses that same organization authorization and the shared timezone resolver, requires a caller-held idempotency key namespaced to the actor and intent, and writes the event plus its organizer grant atomically; a retry adopts that event, while a different key deliberately creates another. The console starts it empty unless the organizer explicitly selects an active template, in which case it invokes the ordinary versioned template application after creation and surfaces a partial result for repair. It never infers a source event or copies proposals, reviews, speakers, files, agenda state, or publication state. The public slug and date range are publishing-owned settings applied separately and actionably, because events carry neither. Name and timezone remain events-domain data: publishing recomposes them into its draft on every preview, while the public snapshot in force changes only at the next site publish and its public slug changes only through publishing's separate address control. Organizations are this domain's records, so **self-serve provisioning is this domain's command**: a first-time sign-in that belongs to no organization is given one named after the person, and then a first event created through the ordinary authorized path with the organizer role it grants. Provisioning an organization is the single write here that names no actor, because at the moment it runs the caller has no membership to be authorized against — the organization is what they are about to become a member of; the caller has already established who is asking, and identity-access is the only caller. The two writes are not one transaction and are ordered so that a failure between them leaves a user holding an organization and no event, which the next sign-in completes rather than duplicating; an organization a signup abandons is discarded by that signup rather than left behind. Provisioning a first event is **idempotent per person per organization**, so two sign-ins racing for one new account converge on a single workspace instead of two identically named events neither of them can delete, and the event and the organizer role on it are written together. A sign-in provisions only into an organization that holds no events **and** has no other member — anything else is somebody's workspace rather than an unfinished one, and a sign-in neither creates an event there nor takes a role on one, including where a role was deliberately revoked. The first event carries a placeholder name and the `UTC` timezone rather than asking for either in the flow: both are one-field edits on settings, and a wrong timezone guessed from a server-side redirect mis-renders every session time on the agenda.
- `PRD-EVT-002` An organization keeps named, versioned **event templates**: a capture of one event's *configuration*, reusable to set up the next occurrence. A template is saved from a source event the actor organizes, and each save is an immutable version recording which event and which person it came from, so an event configured from a template retains the exact version it was configured from as a stored fact rather than a claim. Organization-authorized rename, archive and duplicate exist; archiving retires a name rather than reserving it, and duplicating copies the newest version into a new template rather than re-stamping a history it did not live. A template read or applied across organizations answers exactly as an unknown one does — resolved through the events domain's own ownership query, never from a field in the request. **Applying is a second step, against an event that already exists**, because the actor's grant on a freshly created event does not reach the request that created it; the destination event's own `events:settings:update` is the grant that authorizes the write, and each configuration category additionally enforces its own domain's capability, so a category the actor cannot write is reported as unauthorized rather than silently skipped or raised as a fault. A preview lists every category that would be copied, excluded, or refused as incompatible, and writes nothing. **Events carry no dates** (`PRD-EVT-001`), so the destination range is confirmed as a parameter of the clone and every absolute time in the payload is remapped onto it in the destination's timezone; no deadline or slot time carries forward unchanged. Nothing derived from people or activity is ever copied: no submissions, evaluations, decisions, speaker or contact records, private files or comments, delivery attempts, audit history, published snapshots, credentials, provider secrets, or attendee itineraries. **The CFP's submission window is excluded too**, and it is the one exclusion that is configuration rather than activity: a deadline is a commitment made to a specific audience, and one derived by remapping a previous conference's dates is arithmetic presented to applicants as a promise. A destination with no window reads as an unbounded call — true, and visibly unfinished, so the organizer sets one deliberately (`PRD-CFP-003`). The categories are the CFP form and its routing, review's triage status set and scoring rubric, the agenda's rooms, tracks and time slots, the public page's summary and venue, the speaker portal's resource pages, and speaker task checklists. Message and reminder templates are already organization-scoped, so that category reports *already shared* and copies nothing rather than claiming a copy it did not make. Two of those need saying plainly. **Speaker task checklists did not exist before this**: every task in the system is bound to a real person, so a reusable checklist is a new content-owned concept — an ordered set of titled entries with a due date expressed as an offset, which an organizer later instantiates against named speaker profiles, and which is what a template carries rather than anybody's tasks. And **a cloned resource page's markup is sanitized again on import**, because a stored template payload is untrusted input by the time it is applied; an embed is refused unless the organizer authorizes its host in the destination, since that allowlist is an argument to the sanitizer at save time and is never stored. Applying is idempotent per category — repeating the same application converges rather than duplicating — and it is **not** atomic across domains: a category that fails leaves the categories that succeeded in place and says so, and re-applying is the repair (`ARC-FLOW-006`). What an event still owes is therefore answered **per category rather than per application**, folded across every application it has recorded: a category is outstanding when the newest application that reached it refused it, an application that neither wrote nor refused a category is transparent, and the repair offered is that one category from that one version onto the destination range that application used — never a whole clone, so it cannot write over configuration a later application put in place. Outstanding categories are surfaced both where applying lives and in the operational inbox (`PRD-OPS-002`), so an organizer who never opens the templates page is still told.
- `PRD-IAM-001` Roles are organizer, reviewer, speaker, and public. **A first sign-in provisions a workspace only where one was asked for.** The door a sign-in was started from is recorded on its own attempt row — the callback URL is fixed configuration and a cookie would let the browser decide at return time which of its in-flight sign-ins meant what — and a sign-in started from a public call page provisions an identity and nothing else: no organization, no first event. Somebody who pressed the button there came to keep track of a talk proposal, and a conference workspace named after them is an answer to a question they did not ask. The value only ever *withholds*, so it is not an authorization input and needs no signature: a forged one costs its own sender a workspace they can still obtain by signing in at the front door, which is what an account holding no organization and no event role receives there. The current-session query returns the authenticated identity, organization memberships, event roles, and capabilities used by the application shell. Production sign-in has **two doors and one session**: an emailed six-digit code, and Google OIDC, each offered only where the deployment is configured for it and reported separately by the auth-config read so a surface never shows a door that cannot complete. Both issue the same signed, expiring HttpOnly cookie for the same identity, so memberships, event roles and capabilities are provider-blind; authenticated users may still mint a signed bearer identity restricted to one assigned event. Google sign-in is a redirect the browser follows and a callback it returns on, carrying per-attempt CSRF `state`, PKCE, and a `nonce`, and it trusts an `id_token` only after that token's signature, issuer, audience, expiry and `nonce` verify. A browser may have **several sign-ins in flight at once** — two tabs is ordinary — so each callback completes the attempt its `state` identifies and leaves the others outstanding; a callback presented to a browser that started none of them is refused. Every refusal answers identically and names no check; a failure of the deployment's own is the one outcome told apart, because a person whose sign-in broke on our side should not be told to check an account that is fine. A provider account is matched on the provider's own stable subject; failing that, on the **verified** address the token asserts, which links the sign-in to the identity that already holds it rather than creating a second one — a speaker who signs in with Google stays that speaker. An unverified address is refused, because a claimed address is an account-takeover primitive rather than an identity. A verified provider identity matching neither is a new account, provisioned per `PRD-EVT-001`. **An issued session is a durable record, and sign-out is revocation of it**: the cookie names a session row, every authenticated request checks that the row is present, unrevoked and unexpired, and signing out marks it revoked before clearing the cookie — so a copy of the cookie taken elsewhere, and any event-scoped bearer token minted from that session, stop being accepted on their next request. Sign-out still answers the same way whether or not a session was present, and reports no count, because either would tell an unauthenticated caller whether the cookie it presented was real. A signed-in person may also end **every** session the account holds, on every device, which does report a count because the caller proved that identity first. A session token issued before session records existed names no row and is refused, so the change signs everybody out once. Every identity state change is recorded in an append-only audit log written in the same database batch as the change, and no credential is ever recorded in it. **Organization membership is administered by its organizers.** An organizer may invite an address into their organization or onto one of its events, withdraw an invitation, remove a member, and grant or revoke a role on an event; each is authorized by the capability, membership of that organization, and that the capability was earned on one of its events, so a grant from one organization never reaches another. An invitation is accepted by the accepting session's own identity and never by matching the address it names, which is what keeps a seeded demo identity from being invited into a real organization; an unknown, expired, withdrawn or already-accepted invitation are one indistinguishable refusal. Removing a member or a role takes effect on their next request and does not end their sessions, because they may belong elsewhere. Every one of these actions, and every refusal of one, is recorded in the organization's own audit log, which its organizers can read. Development-only demo switching changes to a signed, expiring seeded identity; it does not bypass application authorization, and a demo deployment that also configures Google resolves both kinds of credential from the same cookie without ambiguity. `ADR-004` records why Google is an additional provider rather than a replacement.
  A demo persona may still use the ordinary single-session sign-out control: it clears the demo
  cookie and returns to the signed-out landing page. Only the separate **end every session** action
  is withheld, because a demo persona has no durable session rows to revoke.
  **Organization-scoped API clients are a separate machine-credential class.** A real organizer
  session creates, lists, rotates, and revokes them; neither a demo persona nor another API client
  can mint one. The `grn_` grammar is unambiguous with event tokens, plaintext is returned only at
  creation or rotation, and only SHA-256 digests are stored. Rotation accepts the previous digest
  for 24 hours. Every request re-reads revocation, expiry, event allowlist, capability scopes, and
  the creating organizer's current grants, then receives only their intersection and exactly the
  owning organization. That tenant identity does not widen event reads beyond the allowlist;
  organization-level scopes are represented separately, and `events:create` grants the new event's
  organizer role to the human who created the client rather than storing a machine ID as a user.
  Revocation therefore takes effect on the next request. Authentication
  records no `last_used_at`, so authenticated reads do not become writes.
- `PRD-IAM-002` Unauthenticated and unauthorized requests remain distinct, use the correlation-aware standard error contract, and reveal no inaccessible object details. The UI provides explicit loading, empty, denied, and recoverable error states, with navigation derived from the active event role. The two new surfaces state the same four. **Sign-in** loads the auth config before offering anything and shows nothing rather than a door that would 404; with no provider configured its empty state says the deployment offers no sign-in instead of presenting a dead button; a returning failure is one recoverable message that names no check, because which check refused is the attacker's answer and not the visitor's; and the denied state is the ordinary unauthenticated redirect. **A newly provisioned workspace** loads behind the same session read as every other surface, and its empty state is the point of it rather than an accident: no proposals, no sessions, no schedule, and a first action for each, so a workspace with nothing in it says what to do next instead of showing empty tables. **The members workspace** states the same four. Its loading state is per-read, so the members table and the audit log each say they are loading rather than blanking the page; its empty states name the first action — invite a co-organizer, or nothing has been recorded yet — rather than showing an empty table; a refusal is the console's ordinary recoverable notice carrying the correlation reference, announced where the control that caused it is; and the surface is withheld entirely from a persona that does not hold the capability. The invitation link is shown once, at the moment it is created, and says so: only its digest is stored, so no later screen can show it again. **Accepting** is its own surface, which the link resolves to and every signed-in person can reach — including a reviewer or speaker, who can reach neither event settings nor the members workspace, and who are who invitations are usually for. It reads the token out of the link so following one is the whole interaction, states a refusal with its correlation reference and leaves the token in place to retry, and on success sends the person into the workspace by a full document load, because the shell it was rendered in was built from a session read that predates the membership it just granted. **Ending every session** is offered beside sign-out and only to a real session — a demo persona is switched rather than signed out, holds no session record, and is refused the action by the API as well as denied the control. Its loading state is the same shared busy state that disables both controls; its success state is not a message but the landing page, reached by a full document load because the console it was pressed in is mounted around a session that no longer exists; and its failure state is the console's ordinary recoverable error notice, which names the correlation reference and leaves the person signed in rather than stranded.

`PRD-IAM-002` also owns **custom event roles and per-field access**. Beyond the four built-in roles an organizer composes named roles on one event — an AV operator, a programme assistant, a sponsor liaison — each a set of capabilities drawn from a fixed allowlist and a set of per-field decisions over the records the role can reach. A field is **View**, **Lock** (readable, not writable) or **Hide** (not returned at all), declared per record kind with a subject-wide default, and a field that identifies the record is clamped from Hide to Lock rather than refused silently, because a record with no identifying field is unjoinable to the person reading it. Administering roles is deliberately absent from the allowlist: a role that could grant capabilities could grant itself the ones withheld from it. Composition across grants is least-restrictive, matching how capabilities already union, and the *absence* of field policies on a built-in grant means unrestricted rather than hidden. **The decision is made once, at the application boundary, and every reader meets the same answer** — a screen, a CSV, an XLSX, a JSON report and an expiring share link all render from the redacted projection, so a field the client hides and the API returns is not hidden. Hidden fields are *absent* rather than blanked, which makes a consumer that forgot to handle them fail to compile rather than print an empty cell that reads as "no phone number on file". Previewing a role resolves the stored role rather than fetching anything on its behalf, so it can never show the administrator's own data wearing the role's name. Separately and with the same vocabulary, an event carries **portal field locks**: what the person whose record it is may still change on their own portal, replaced as a whole set rather than toggled per field, merged onto every non-organizer grant at the stricter of the two. A lock is a property of the event rather than of anybody's staffing — a speaker holds no custom role, and freezing biographies once the programme is printed should not touch next year's event. Reading personal data unmasked in a report is its own capability, `reports:pii`, held by neither role by default and requested explicitly per run; holding it is not the same as exercising it, and exercising it is recorded.

Field-governed mutation contracts are partial, and enforcement considers only fields whose
values actually change. An absent hidden field or an unchanged locked field therefore cannot
prevent the holder from editing an allowed sibling.

## CFP, abstracts, and review

- `PRD-CFP-001` Organizers compose ordered typed fields, required rules, guidance, conditional visibility, category-based status routing, open/close state, preview, and publication. A visibility condition references an earlier question and is evaluated identically in the organizer preview, public applicant form, and server validation. Editable drafts use optimistic concurrency: every save names the version loaded by that editor, exactly one competing save advances it, and a stale save is refused without replacing the winner. Publishing and closing are separate decisions: publishing replaces the form applicants see and preserves whatever open/closed state the live call already had, so republishing a closed call never reopens it and only the explicit reopen action can. A first publication has no live state to preserve and opens the call.
- `PRD-CFP-002` Submission is server validated and idempotent; applicants get a durable confirmation identifier. Hidden fields are neither required nor accepted, and the first matching routing rule resolves a CFP-owned triage status that is persisted with the form-field snapshot rather than recomputed after form edits. **A routing rule may not name a decision.** `accepted` and `declined` are reached by recording a decision — the act that creates the session and tells the submitter — so a rule naming one is refused when the form is saved, is offered by no composer control, and is ignored rather than honoured if it was stored before that refusal existed: the proposal takes the default triage status, and the submitter is told it is under consideration rather than that somebody accepted it. It is the only unauthenticated write, so it is bounded: a submission carries at most 40 answers, each within the `maxLength` its published field advertises, and repeated submissions from one address are throttled. The counter is keyed on the caller's address alone — never on anything the caller supplies, such as the event id in the path — because a caller who can mint counter keys can evict its own spent counter and start again.
- `PRD-CFP-003` A call has a scheduled submission window of two optional instants, entered and displayed in the event's timezone and stored as instants so an announced deadline cannot move when the timezone is corrected. It is live state alongside open/closed, not part of the published form, so setting or extending it takes effect without republishing and publishing a form never opens a call the schedule keeps shut. **Both gates must permit a submission:** the schedule cannot open a call an organizer has closed, and reopening is refused — naming the deadline as the thing to move — when the deadline has already passed, because it would otherwise change nothing an applicant can see. A call before its opening is `scheduled` rather than `closed`, and both states are stated to applicants with their date. The effective state is computed by the server and carried on every response, so no client decides from its own clock whether a deadline has passed. A surface that has already read that state re-reads it after any write that could have changed it, and the public page re-reads it when its tab returns to the front, so a deadline that has passed stops offering a form without a manual reload (issue #222).

  **The deadline is announced rather than only enforced.** A submitter holding an unsubmitted draft is written to once inside the two days before it, and an organizer once after it, both on a scheduled trigger and both idempotent per `(event, recipient, deadline instant)` — so moving a deadline is a new fact and a cron that ticks every minute is not (issue #210). **The draft holder was never asked to be reminded, and this is the decision not to ask them.** The message is about that person's own unsubmitted draft, on the event they created it on, addressed to the account address identity holds — the same address that already received their submission confirmation, which is what established the channel — and it is sent at most once per deadline and says in its own words that nothing further will be sent about it. There is no second use for the address and no other message this consent could be read as covering. A decline control is the alternative and stays available if that judgement is ever wrong; what would be wrong is to send and leave the recipient no statement of it.
- `PRD-CFP-004` A submitter may hold proposals against an account. A proposal has one owner and it is the authenticated session, never a form answer; the owner is immutable, and every read and write is scoped to it so a proposal belonging to somebody else is indistinguishable from one that does not exist. A draft is held to the published form's shape but not to its completeness, so a minimally populated proposal survives a closed browser and can be resumed and submitted later; submitting is one-way. **A proposal resumed after the form moved on keeps only the answers the current form still has a visible question for**, and is told so: a revision is validated against the current form, so an answer to a question since removed — or since hidden by a condition — would refuse every save and every submit, and the refusal names a field the page cannot show, because errors render beside visible questions. Dropping those answers is what keeps the proposal editable at all, and it is stated on screen before the save that makes it permanent rather than discovered afterwards. That rule binds every control that could replace what an applicant has typed, not only this one: re-opening the proposal already in the form leaves the typing alone, switching to a *different* proposal is refused while there is typing to lose rather than silently taken, and the one control that discards on purpose says what left with it. **Whether the call is open is the server's answer and is never recomputed in the browser**: the organizer's status line, the public banner, the availability of the form and its submission controls all derive from one effective state the server computed for that read, in both directions — a deadline moved into the past closes the call and one moved back into the future reopens it — and no surface claims a closure the server has not accepted. Answers that are merely *wrong* — too long, a malformed address, an option that no longer exists — are kept, because those land on a question the applicant can see and fix. Revisions use optimistic concurrency: every write names the revision it read, exactly one competing write advances it, and a stale write is refused without replacing the winner. Editing and submitting are refused at the application boundary once the call is not open, while reading stays available. A submitter is shown `draft`, `under consideration`, `accepted` or `not accepted` and never a configured triage status. **Guest submission remains supported and remains anonymous:** the unauthenticated write records no owner, so it reaches no dashboard, cannot be edited, and cannot be claimed by asserting an address. At most one confirmation per proposal is queued through communications' public interface, addressed to the account's own linked address — never to an address the request supplied — and a later revision confirms nothing again. An account with no linked address is recorded as unaddressable and receives none, which is why the dashboard rather than the message is the guarantee the product makes. The anonymous door sends nothing at all. "Linked" is what identity stores; this system holds no proof of control beyond whatever the sign-in door established, which on a demo deployment is nothing (`GAP-027`).

  A published select question may carry stable choice identifiers independently of display labels. Reserved `track` and `format` choices are stored as first-class proposal classifications only while active; removed or inactive choices remain only in the immutable answer snapshot. A proposal may also hold at most eight structured co-speakers or moderators, each with a stable id, normalized address, explicit role, and pending/accepted/declined state. The owner may add, edit, or remove pending participants while the call is open, but cannot rewrite an accepted participant's private identity. Only the signed-in identity linked to the invited address may accept or decline, under the proposal's deadline and revision guards.
- `PRD-ABS-001` Organizers filter, assign, bulk-transition, and audit submissions through configured statuses. A draft is not a submission and reaches none of these surfaces. The default `submitted` status cannot be removed from an event while a draft is waiting on it, because submitting that draft is what will need it — the refusal lands on the organizer's configuration change rather than on the applicant's Submit.
- `PRD-REV-001` An evaluation plan defines criteria and scales. Reviewers see assignments, conflicts, completion, and no aggregate bias before submission.

  Blind review is a server-side allowlist projection. Only `title`, `abstract`, `track`, `format`, and `tags` answers may reach a blind reviewer; submitter identity, participant records, biography, company, job title, contact details, social links, assets, and file metadata are absent from the reviewer transport and assistant input. Organizer projections retain the complete authorized proposal. This allowlist supersedes the historical heuristic description in the detailed workflow paragraph below: arbitrary short- or long-text identity content does not reach a blind reviewer.

`PRD-ABS-001` organizers configure an ordered event-scoped status set, filter proposals by those statuses, and transition a selected set atomically; each successful transition displays its transaction-current prior status, next status, proposal, actor, and occurrence time. The status set always contains the reserved decision statuses `accepted` and `declined`, which no configuration may remove; they are not transition destinations either. Reaching one of them is the *effect* of a recorded decision, so a transition into either is refused and names the decision command instead — a status change into `accepted` wrote a board state with no decision behind it, and the content domain then refused the very proposal the board showed as accepted. A proposal projection carries the submitter's name and contact address derived from the answers using the published form's field types; those details are organizer-only. The reviewer queue projection removes the derived contact object and replaces the derived display name with a fixed mask, and the answer list it carries never contains an `email`-typed answer or an answer whose field is identified as the submitter's name. That identification is a heuristic over the published form's own field types, ids, and labels, so it is exact only for details the form collected in a field it typed or labelled as such: an address a submitter types into a `short_text` answer, or a name inside a `long_text` biography, is not detected and still reaches the reviewer. Blind review is therefore a projection guarantee about identified fields, not a content scan. `PRD-REV-001` organizers configure numeric, dropdown, and free-text criteria with explicit weights; only numeric values contribute to the weighted aggregate, while every criterion value remains visible in organizer results and CSV export. Organizers may assign a proposal once per round to a user who holds the reviewer role for that event, or deterministically distribute a selected set across reviewers up to a per-reviewer cap. A round is a first-class configured object: it has a name unique within its event, an optional open/close window, a lifecycle state of `draft`, `open` or `closed`, an anonymization policy, an optional scorecard of its own, and a reviewer pool that is either every reviewer the event staffs or a named list. Its identity is the ordinal number every assignment, outcome and suggestion of that round already carries, so making rounds first-class moved no existing row. Work is recorded in a round only while it is `open` and inside its window, and only for a reviewer the round admits — assignment, distribution, advancement, saving scores, declaring a conflict and accepting an assistant's draft are each refused otherwise, naming the round and the reason. A pool is keyed on its round, so membership in one grants nothing in another; a reviewer already holding work in a round cannot be removed from its pool until that work is unassigned. A `closed` round is view-only and permanent: its window, scorecard, anonymization policy and pool are frozen, though it may be reopened. A round's own scorecard, where it has one, is what its reviewers are shown, what their scores are validated against, and what its weighted aggregate is computed from; without one the round scores against the event plan. Anonymization is per round: a blind round's reviewer projection carries no submitter name, no contact object and no co-author list at all, while an open round's carries the author's name and the co-author roles and still withholds the contact address, which is organizer-only in every round. The assistant's input is identity-free in every round regardless of that policy. An event that has never configured a round behaves as one with a single open round admitting every reviewer it staffs. Advancing a status-filtered set creates the next round, inheriting the previous round's anonymization policy and scorecard and taking its pool from the reviewers the advance distributes to; assignments, completed evaluations, and organizer outcomes remain round-scoped, so using the same reviewer again never overwrites prior-round history. The assignable list excludes the signed-in actor and the assignment command refuses that identity, because the organizer console exposes no reviewer queue, so assigning to oneself would create an evaluation nobody can open and would lock the rubric for good. Organizer progress names assigned, completed, and outstanding counts per reviewer and per reviewer per round. An organizer may remind selected reviewers who still owe evaluations in a round; the reminder is requested through the communications public interface, is delivered once per reviewer per round however often it is requested, and the response states for each reviewer whether it was queued, had already been sent, could not be addressed, or was not sent because nothing was outstanding — the outstanding count being recomputed at the moment of the request rather than taken from it. Review writes no communications table and invents no lifecycle event. Organizer results carry every completed evaluation's criterion values and written comment with its reviewer and completion time, labelled by the criteria of the round it was recorded in; unfinished drafts are not organizer-visible on any surface, and no reviewer projection ever carries another reviewer's evaluation. An organizer records an accept or decline decision on a proposal, which moves it to the matching reserved status and stores who decided, when, and why; that stored decision — not the status label — is what authorizes the proposal to become program content. The rubric is locked once assignments exist. An organizer may remove an assignment, which takes any draft evaluation and declared conflict with it and — when it was the last one — releases that lock, so a mis-assignment is a correctable mistake rather than a permanent freeze of the event's criteria; removal is refused once that reviewer has completed an evaluation, because its score is already counted in the proposal's aggregate and has emitted the completion event. Reviewers can access only their own event assignments, declare a conflict, save a validated draft, and complete it. A conflicted assignment cannot be evaluated; completion is terminal and atomically persists the evaluation, aggregate outcome, and one idempotent completion event. Reviewer responses never contain aggregate outcomes; organizers receive an outcome only after at least one completed evaluation in that round. Completion publishes version 1 of `EVT-REVIEW-COMPLETED` with organization/event/proposal/assignment scope and correlation/causation metadata.

## Speakers, content, and CRM

- `PRD-SPK-001` A person has one event-scoped speaker profile linked to sessions, tasks, assets, messages, and optional CRM origin. The accepted-speaker roster searches names and companies independently of session search and combines that query with readiness without changing the underlying event-scoped collection. Speakers and event organizers edit the same canonical name, pronouns, job title, company, bio, social links, and chosen headshot. Every such write names the profile version the editor read; one winner advances it and a stale write is refused rather than silently replacing the other person's work. Text, headshot selection, replacement, and removal use the same revision command and append an attributed unified-audit record naming the resulting version. Replacing or removing a headshot returns the prior object to private in that same write, so its anonymous URL stops answering unless another still-published projection legitimately owns it. Public projections allowlist the canonical bio, job title, company, social links, and publishable chosen image rather than reading an organizer-only copy.
- `PRD-CNT-001` A session owns title, abstract, format, speakers, tags/tracks, and publication state. It does not own a time: when and where a session happens is its placement on the event's *published* agenda, resolved through the agenda's public application interface every time a session is projected, so the speaker portal, the calendar export, and the published schedule can never name different times for one session. A session the published agenda does not place carries no schedule at all rather than a remembered or invented one, and a placement the organizer has moved but not yet published does not move it. Acceptance names only the proposal: title, abstract, format, and speaker identity are resolved through the review domain's public application interface and the speaker conversion port, so an unknown, foreign, or undecided proposal is refused and no caller supplies a speaker identity. Acceptance is idempotent per event and proposal, and the session stays editable afterwards. An organizer may withdraw a session, which removes it and every agenda placement holding it through that same interface — the reversal path for an abstract that was accepted and later declined — while the speaker's profile, tasks, and uploads survive, because one withdrawn session is not a reason to delete a person's work. Once the event site is live, the next public read reconciles accepted-content changes into a new immutable publishing projection version; an unpublished event remains unpublished.

  Acceptance also carries the proposal's stable source track and format identifiers and provisions the submitter plus every accepted structured participant as speaker profiles linked exactly once. Pending or declined participants do not become speakers. A removed classification remains source provenance and is never reconstructed from its label; retrying acceptance returns the existing proposal-linked session without duplicating speakers, tasks, or metadata.
- `PRD-SPK-002` The portal is task-first and exposes completion, due state, profile preview, uploads, headshot selection, and calendar download. A speaker names which of their own uploads is their headshot, and an organizer of the event may name or remove it for them; nobody else may, and a file that belongs to another profile or is not an image is refused as a named field error. Naming a headshot is not publication: the chosen file keeps the visibility it had, the public gallery shows initials until an organizer marks that file publishable, and deleting the file clears the profile that pointed at it so no snapshot advertises a URL the asset route would refuse. The calendar download exists only while at least one session is scheduled, because an iCalendar object must carry at least one component; "scheduled" means placed on the published agenda, so the file a speaker imports carries exactly the instants and rooms the public schedule serves, and a session the published agenda does not place is left out of the file entirely rather than exported at an invented time. An organizer may also send one iTIP `REQUEST` per speaker and session. Repeating an unchanged send is idempotent, while every schedule or recipient-address change queues another `REQUEST` with the same `UID` and a strictly greater `SEQUENCE`, including a session returning to a time it held before, so a calendar client replaces the entry it currently holds. Uploads stay private until an organizer publishes them, and every publication is reversible: an organizer may return an asset to private, the uploading speaker or an organizer may delete it along with its stored bytes, and an asset is served anonymously only while its event's public page is live, so unpublishing the event withdraws what that page exposed. An asset a caller may not read is answered exactly like one that does not exist.

  Organizer-authored resource pages extend that portal. Body markup is sanitized through a strict parser-backed allowlist before storage, hidden pages never reach speakers, and reference embeds accept one HTTPS iframe only from the configured host allowlist. The browser renders that embed in a sandbox without script or same-origin privileges, while a refused host produces an actionable validation error.
- `PRD-CRM-001` Prospects have stage, contacts, notes, activities, owner, next action, and conversion preserving provenance. Ownership may only be given to a user identity-access reports as staffing that event — its organizers and reviewers — resolved through a public application query rather than a read of identity tables; an unknown or foreign-event owner is refused as a named field error, and being assignable grants no CRM access. Every stage transition appends exactly one `stage-change` activity naming the prior and next stage, written atomically with any note recorded by the same update. The repository derives that prior stage from the row its write actually moves, not from the service's earlier read, so interleaved moves form one truthful chain. A pipeline-stage save is likewise decided against committed card rows: removing a stage that acquired a card after the board was read aborts the write and keeps both the stage and card, while the explicit migrate-and-delete command moves the matching committed set and records that same set's history in one batch.
  The CRM also holds an organization-wide **contact directory** spanning every event of one organization: searchable and filterable by company, title, tags, and custom fields, with those filters savable as named segments that store their definition rather than a frozen membership list. A person appears exactly once — enforced by a partial unique index on `(organization_id, email)` among un-merged records — and carries every event that has courted them, each event's stage read from that event's prospect so the directory can never claim a conversion the pipeline does not have. Contacts arrive by hand or by CSV import, which is previewed row by row against the live directory by the same code that then commits it, and which enriches rather than overwrites: a note somebody typed survives, the file's own values win where both name the same field, and a row that would *raise* a contact past what one may carry — twenty tags, thirty custom fields — is refused by name, in the preview as well as the commit, rather than applied by discarding something. A contact a merge has already left above that ceiling still accepts rows that add nothing to it. Near duplicates — the same person entered under a work and a personal address — are detected on name and company, and merging folds them into an explicitly chosen primary: nothing is deleted, history and event links move to the survivor, and the merged-away addresses stay searchable as aliases. One exception, because a contact holds at most one link per event: where both records were already sourced into the *same* event, the survivor keeps its own link and the loser's stays on the merged-away row. That row is retained, so no history is lost, but the survivor's event list shows one link for that event rather than two. Bulk outreach to a selection or a segment is previewed before it is sent and then delivered through communications' interface, which the CRM reaches through a port it declares itself and never by importing that domain. Organization-level metrics are counted over stored contacts, never constants.
  Directory access is authorized **at the organization**, and by three conditions together: `crm:manage`, membership of that organization, and that the capability was earned on an event *of that organization*. The third is what stops a capability granted by one organization from reading another's directory when the actor happens to belong to both (`ARC-AUTH-001`, issue #27). Sourcing a contact into an event additionally requires the event-scoped `crm:manage` and that the event belongs to the organization, so an organization-wide grant is never a licence to write into an event the actor does not run. Conversion continues to run through the existing idempotent speaker-conversion command with its existing key: pushing a contact into an event creates or reuses that event's prospect and converts *that*, so a contact pushed twice yields one prospect and one speaker and every provenance record written before the directory existed keeps its meaning.

### Residual review, private-content, and sourcing behavior

`PRD-REV-001` treats the published CFP select field whose reserved id is `track` as the proposal's track. The submitted snapshot is immutable review input; after acceptance content carries that value until a scheduled agenda placement supplies the public display track. Organizer exports provide CSV and XLSX with identical visible rows and formula-safe cells. A round also owns instructions, a frozen filter snapshot, reviewer-visible fields and file policy, per-proposal evaluation cap, invitation occurrences, and an optional weekly reminder in the event timezone. Weekly reminders run only for open work and are keyed by local-date occurrence so DST changes and replay do not duplicate them. Accept, waitlist, request-revision and decline are numbered decisions with immutable history. An organizer may invite all or only newly assigned reviewers and receives per-recipient delivery state. An AI persona is configured per round; suggestions remain distinguishable drafts, never enter human aggregates until separately accepted and completed, and organizer reporting exposes aggregate draft state/model counts without exposing reviewer-private text or scores.

`PRD-SPK-001` private sets may name view or edit collaborators who already belong to the event; removing that event assignment removes the collaboration's authority, and the collaborator's event field policy still governs every read and write. Profile and asset capability links reuse the platform's hash-only token convention, with bounded expiry, optional password and view limit, indistinguishable anonymous refusal, and organizer-only create/list/revoke controls. Profile and session remix use a content-owned provider port and return an explicit draft without writing canonical content; a visible-but-locked source may be drafted because that does not save it, while a hidden source is refused before its value reaches the provider. Portal profile, session and workflow writers enforce event field View/Lock/Hide policy at the application boundary, and hidden fields are omitted from the projection rather than hidden only by the client. Workflow status is event configuration with a stable key, editable label and closed semantic category of open, ready or blocked; an in-use key cannot be removed. SMS is explicitly outside this release under `DEBT-015`: shipping it requires verified phone ownership, consent and opt-out semantics, channel-specific templates and a provider port together.

`PRD-CRM-001` accepts year-round public speaker interest through the same client-address throttle and honeypot boundary as the public CFP, normalizes and deduplicates the mailbox, and creates at most one entry-stage prospect. Campaigns persist an immutable audience and template with draft, scheduled, running, completed or cancelled lifecycle; the scheduled tick launches due work and delivery idempotency is per campaign and contact. Engagement ingestion is idempotent on provider reference and kind, projects a fact onto both directory and sourced-prospect timelines, and bounces or unsubscribes suppress future direct and segment outreach. Directory analytics consume the transition history to report funnel edges and average conversion time rather than constants.

## Agenda, communications, integrations, public

`PRD-SPK-001` at event scale includes CSV preview/import with explicit invalid and duplicate dispositions, persistent workflow/logistics/custom fields, and bulk assignment of general or file-request tasks. An import row whose speaker record is removed while the import is running is **refused and reported by name**, never silently skipped and never fatal to the rest of the file: the row is counted as neither imported nor valid, the import ledger keeps it pending, and re-running the same file re-attempts exactly that row and converges, because convergence is keyed on the normalized address rather than on the attempt. The same reading applies to the ledger's own mark of completion — a row counted as imported that nothing recorded as complete is a claim storage does not support (issue #202). `PRD-SPK-002` associates uploads with requested tasks or sessions; re-upload creates a numbered latest version without withdrawing earlier readable versions. Speakers and organizers may leave attributed, timestamped asset comments. `PRD-CNT-001` records attributed immutable revisions before profile and session edits, and organizer restore writes another revision rather than erasing history. The revision and the edit it describes are written together or not at all, and the number a revision carries is allocated by that write, so two people editing one speaker are numbered in turn rather than one of them being refused (issue #116). Organizer ZIP export accepts selected latest deliverables only and emits deterministic names and contents. An event's **speaker checklist** — the ordered, titled lines `PRD-EVT-002` describes, each with a due date expressed as a signed day offset — is written and maintained from the content workspace: an organizer adds, reorders, edits and removes lines addressed by row, and separately instantiates the checklist against named speaker profiles, which is the act that creates dated tasks and tells those speakers about them. The two are separate on purpose, because declaring configuration and writing somebody's work are different decisions. A title another line on the event already holds is refused rather than converged on, and removing a line leaves tasks already assigned from it in place: a task is keyed by the title it was given and holds no pointer back, so once assigned the work is that speaker's. Instantiating is idempotent per speaker and line, so running it again after a speaker joins brings only the newcomer up to date — and so is the telling, so a second run announces nothing to the people it assigned nothing to. Recording a message, a comment or a revision still creates no notification or delivery effect of its own: what enqueues is a lifecycle *action*, through the port the domain taking it declares — content's for accepting a proposal and for requesting or instantiating a speaker's work, review's for a decision — and communications owns everything past that under `PRD-COM-001`.

- `PRD-AGD-001` The agenda manages event-scoped rooms, tracks, timeslots, and placements over sessions supplied by the content application query. A placement may be added, moved, or removed in a private draft. One assisted action seats the unscheduled sessions — every one of them, or exactly the subset the organizer selects — in a single draft revision, without introducing a conflict and without moving a placement made by hand; what it cannot seat stays unscheduled and says why, the control naming which of the two it will do, and the result is ordinary editable draft state. Overlapping placements explicitly identify every shared room, speaker, or session and give a resolution; a conflicted draft cannot be published. Publication is an organizer-only, auditable action that creates a numbered immutable snapshot. Where the snapshot in force puts each session, and at which publication that last meaningfully changed, is **derived state that is stored rather than replayed**, and the system treats it as derived: the database itself records whether the stored answer still describes the publication history, whoever wrote that history, and an answer that has fallen behind is re-derived from the immutable snapshots before it is served, swept up on the scheduled tick for events nobody reads, and reportable and repairable on demand without a repair being the price of asking. A repair is never silent, whichever path performs it: every one is recorded, because a schedule that quietly corrects itself would hide whatever is writing publications behind the derivation's back. The agenda is also the single source of a session's time for every other domain: `ContentAgendaInterface` answers where the snapshot in force places each session, and withdrawing a session drops its draft placements, so no other domain stores a second copy of when a session happens. Only the latest snapshot—not subsequent draft edits—is available through the public schedule projection. Publishing that snapshot emits `EVT-SCHEDULE-PUBLISHED`; in the same D1 batch, publishing refreshes an already-live site's immutable projection and records the agenda version and time as provenance. It never creates a public site. The public schedule response and every page/embed then read the same publishing-owned projection, so a session on the board whose content is still a draft is never public and no room, track, slot, placement, session, or speaker storage identifier leaves the agenda.
- `PRD-COM-001` Templates and triggers enqueue immutable delivery attempts with retry and terminal state; sent history is auditable. **Every organization holds the lifecycle templates, not only a seeded one.** A message resolves a template scoped to the organization, so an organization with none sends nothing at all — silently, because the composition root must not fail a committed action for a message. The catalogue is therefore provisioned as rows the organization owns: backfilled for every organization that already exists, and materialized on the first resolution and the first time an organizer lists them, so an organization created later needs no signup-time write. It is provisioned as version 1 only, and only for a key with no rows at all, so an organization that has published its own wording keeps it for ever — editing a message is publishing the next version, and that is the feature organization scoping exists for (issue #217). **A subject with two possible addresses is written to at the one their account proved.** Some subjects have both: an address they proved control of by signing in, and an address they typed into a public form. The two are not equally trustworthy and this domain states the rule once, and it is about *which subject* rather than which address: **an account-bound subject is written to at its account, or not at all.** The form address is reached only when there is no account — a guest submission, which is a supported way to apply (`PRD-CFP-002`) and where telling nobody is the only alternative. An account holding no address therefore sends nothing rather than falling through to a form answer, because on an owned record that answer is still unverified and possibly a stranger's; the product's guarantee there is the dashboard, not the message (`PRD-CFP-004`). The guest path answers a *known* fact only — that there is no account. A lookup that **failed** is not that, and sends nothing — falling through on a transient error would choose the less trustworthy address on no evidence, and a delivery key that already names the occurrence converges on the wrongly addressed row rather than correcting it. The domain reporting the lifecycle fact reports both and resolves neither, because an address is identity's to answer for; the composition root is where the fact meets identity's answer about the same person, and so is where the choice is made. No address at all is reported as unaddressable rather than queued, because a delivery to a non-address burns an attempt and fails with the provider's complaint about syntax instead of the reason. This is what bounds `#132` to guest submissions; the residual and its enrichment guard are `DEBT-013`. **What remains of that residual is bounded rather than removed.** A delivery whose recipient came from a form answer is declared as such by the caller that resolved it, and one event may write at most three such messages to one address — enough for a decision and its reversals, and few enough that a hundred guest proposals naming one victim cost that person three messages rather than a hundred. The count is derived from the deliveries themselves rather than from a counter, so it cannot drift from what was actually sent, and it is scoped to the event, because an address that agreed to hear from one conference agreed to nothing about another. Two things it counts are stated exactly, because a bound that is wrong about either is not the bound it claims. The address is compared as a **mailbox** — case-folded, with any `+tag` removed — since one inbox spelled several ways would otherwise hold several budgets. The folding is ASCII-only, because it has to be the same folding the stored rows are compared under; the residual, that non-ASCII case variants of one mailbox are still separate budgets, is recorded in `GAP-027` rather than left inside the word "mailbox". And only a delivery whose recipient the caller **declared** is counted: a message addressed at an account cannot exhaust a guest's budget or be exhausted by it, because refusing an organizer's decision notification to a speaker whose address the product does verify would be a bound on the wrong thing. The count is read before the write rather than atomically with it, so simultaneous enqueues can both pass at one below the cap and the overshoot is bounded by request concurrency rather than by the number itself — which is what "a bound on amplification" means here, and why it is stated rather than rounded to three. **The submission is never refused for it**: a proposal cannot fail because somebody else mail-bombed that address, so the cap refuses the message and the organizer is told on the event's own timeline that a decision notification did not go out. It is a bound on amplification and not a verification — an unverified address still receives up to three messages, which is why `#132` stays open.

  **A lifecycle message that cannot be sent at all is reported where an organizer reads it.** The composition root must not fail a committed action because its message could not be queued, so it catches — and that catch was written for a transient storage failure. A missing template and a reached recipient cap are neither transient nor invisible-by-design, so both are recorded on the event's timeline beside the action that should have sent them, keyed so a permanent condition is recorded once rather than on every repetition (issue #217).
- `PRD-INT-001` SQL is canonical. Two integrations exist and each is one-way; naming them separately is the point, because they run in opposite directions over the same third party. **Outbound:** Airtable and Accelevents receive versioned projections through typed ports, and Greenroom owns every field they carry. **Inbound:** Accelevents is the registration platform of record, and its registrations are read into Greenroom as speaker profiles — the direction that eliminates manual re-entry, which is what the brief asks for. The inbound sync never writes another domain's tables: it goes through content's own public import command, so a preview writes nothing, a row is validated before it is accepted, and applying twice converges on the same speakers instead of duplicating them. Convergence is keyed on the **normalized email address**, through content's speaker-import ledger, rather than on the Accelevents record reference: two registrations sharing one address are therefore one speaker, which is the right answer for a person who registered twice and a deliberate departure from a per-record reading of idempotency. Registrants carry their Accelevents reference onto the profile they become, so provenance survives even where identity is collapsed. **Status:** outbound projection state, versioning and the outbox are implemented, and an HTTP adapter exists for each of the three delivery channels behind the credential-gated `COMMUNICATIONS_PROVIDERS=live` switch. The inbound sync is implemented with an organizer surface — preview, apply, last-run state and its failure — and runs on a deterministic in-repository roster by default, which is what lets the demo and a fresh clone sync with no credential. **Nothing here has reached a real Accelevents tenant:** no credential exists in this repository, every adapter test stubs `fetch`, and the staging smoke has not run, so a live sync's request shape is a documented contract rather than an observed one. The Airtable *product* surface the brief implies — organizer-visible field mapping, connection test, dry-run preview — still does not exist (`GAP-012`, issue #23's Airtable workflow).
- `PRD-PUB-001` Only published projections are public. Event hub, multi-day schedule, sessions, speakers, CFP, itinerary, configured embeds, and the JSON programme feed all read one publishing-owned projection. Preview and the first site publish compose event metadata plus the published CFP, accepted content, and agenda through public application interfaces; publishing never reads another domain's tables. A site publish establishes a monotonic immutable projection version and records its source provenance. Afterwards, agenda publication refreshes that live projection atomically through `EVT-SCHEDULE-PUBLISHED`, while successful public reads reconcile CFP and accepted-content changes and append a version only when public bytes or provenance changed. None of those source actions creates a public site for an event that has never been published. The public page's own fields — summary, venue, the two dates and public address — remain deliberate draft data and reach visitors only through an explicit site publish. Every public address is a readable, stable, non-storage slug. The schedule response is addressed by the public event slug, carries the agenda version/time recorded in the active projection, and returns exactly the placed sessions from that projection; therefore pages, embeds, and JSON cannot disagree after a schedule publish. Session discovery searches titles, abstracts, and speakers and combines Track, Format, and Location facets. Detail pages expose time, duration, room, track, format, speakers, photos, organizations, and related sessions from the same version. Attendees remain anonymous: an itinerary stores only published session slugs behind an unguessable capability token whose hash is persisted, and the itinerary embed can resolve a shared `plan` token without exposing account or private data. Itineraries are filtered against the active projection on read and write and stop answering when the event is unpublished; retention and capability-URL limits remain as documented in `DEBT-012`. Unpublishing removes the active public projection immediately but preserves version history and makes event, schedule, asset, itinerary, embed, and JSON routes return the same not-published response used for unknown slugs. Public reads remain credential-free, cross-origin readable, and validator-cacheable: every public 200 carries a strong ETag and `no-cache`, and no non-200 public response is stored.
- `PRD-PUB-002` An organization composes one **branded portal** over several programs at one readable address. A portal carries its own landing and sign-in copy, a theme and a primary colour, an ordered list of the programs it lists — a call for proposals, an interest form, a speaker portal — the fields its own registration form asks for, custom pages, and the privacy notice registration records against. Program references are held as `(kind, ref)` pairs with no foreign key, because publishing does not own the programs it lists; a reference whose source has gone is reported as **unresolved and kept in the visitor's order** rather than dropped, since a portal that quietly shortened itself would say nothing about why. **Publishing is refused until a privacy notice exists**, because registration stores the notice version somebody accepted and a live portal with no notice would record consent to nothing. The notice is append-only and so is the consent record: neither can be rewritten, so a consent can always be traced to the exact words accepted. The version recorded comes from the stored portal and never from the request, since a client that supplied it could claim consent to a version the visitor never saw. Every save carries the revision it read, so two organizers cannot interleave into an arrangement neither chose. Slugs are unique, readable and non-storage, and a taken slug is a conflict rather than an internal error. A registration answers only the fields the organizer configured — an unconfigured field in the request is dropped rather than stored, because a registration is bounded by the form and not by what a caller chose to send. HTML in a custom page passes publishing's own allowlist, which admits no image, frame or style. **There is no delete for a portal**: it is unpublished, which removes the public projection immediately and preserves its publication history.
- `PRD-AI-001` AI may draft or summarize but never silently changes canonical state; manual fallback is required. A suggestion is offered to one reviewer for one assignment in one round, drafted from the same masked projection that reviewer reads — so the submitter's identity never crosses the provider boundary — and stored with the model, prompt version, time and abstract revision it came from, all four of which are shown to the reviewer with the draft. Nothing the provider returns is a score: suggestions are stored apart from evaluations and no aggregate reads them. A reviewer either dismisses a suggestion, which writes no evaluation and leaves only the audit row, or accepts it, which writes **their own evaluation as a draft** carrying the suggestion's id; completing that draft is a separate reviewer action and is the only thing that moves an aggregate. Storage enforces both halves rather than trusting the service: a suggestion cannot leave `offered` without a named responder, and an evaluation cannot claim a suggestion that is not its own reviewer's. The port is credential-gated with a deterministic fake as the default and an `off` mode that withdraws it entirely; a provider that is slow, throttled, unusable or absent surfaces as a visible notice beside a scoring form that still works, and a half-configured live mode refuses rather than silently drafting with the fake. **Status:** implemented and live-verified (issue #110, `GAP-011` closed). The 2026-08-13 staging smoke covered the deployed fail-safe, schema-valid generation and provenance, draft-only persistence, separate completion, failure normalization, manual fallback, and the identity-free outbound request; no credential exists in the repository and ordinary tests still stub the provider boundary.

`PRD-INT-001` also owns signed outbound webhooks. An organization, optionally scoped to one event, subscribes to typed versioned facts; schedule publication fans out idempotently per `(subscription, event record)` into an independent three-attempt queue. Payloads contain identifiers and publication version, never speaker, reviewer, CFP, or proposal content. Exact body bytes are HMAC-SHA-256 signed, timestamps limit replay to five minutes, and rotation emits both signatures for a 24-hour overlap. Destinations are HTTPS-only, screened for non-public hosts at subscription and send time, never follow redirects, and never retain response bodies. Management and immutable attempt history require organization-scoped `communications:manage`; manual replay appends an actor-attributed request attempt before requeueing.

## Operations across domains

- `PRD-OPS-001` One event-scoped search answers across every operational surface the caller can already open, and it is authorized **per source rather than per surface**. The request itself requires a session and `events:read` on the named event; each source inside it is then composed through the owning domain's own public application interface, under the capability that domain already enforces — sessions, speakers and tasks under `content:read`, proposals under `review:manage` for an organizer and `review:evaluate` for a reviewer, agenda placements under `agenda:manage`, deliveries under `communications:manage`, prospects and directory contacts under `crm:manage`. A source the caller may not read is **omitted and named as omitted**, never refused and never reported as an outage: the answer says which sections the caller's role does not include, and the sections that did answer stay usable. Any other rejection degrades exactly its own section, which reports its own correlated error while every other section still renders. There is no search index and no projection storage: private CRM notes, unpublished speaker material and reviewer-hidden aggregates keep their original rules by construction, because the only way this reaches them is the call the console itself would make. Blind review holds structurally — the reviewer projection is chosen by role rather than reached and recovered from, so a reviewer's results carry the masked submitter and never the organizer's. Results are scoped to the named event and carry no record of a sibling event in the same organization. Every hit carries the console path the server produced for it, including its event, because which surface a record opens depends on the role that read it. A query shorter than two characters is a field-level refusal rather than a scan, and every section is capped, so the cost of a keystroke is bounded. The surface states loading, empty, role-omitted and per-source-failed explicitly rather than rendering a heading over nothing.

- `PRD-OPS-002` One event-scoped operational inbox states everything waiting on an event, in six categories: configuration the event was cloned into and never received, agenda conflicts and unplaced sessions, outstanding speaker work, evaluations nobody has completed, deliveries that failed, and a public page behind what the organizer has composed. The configuration category is the events domain's own answer to “what does this event still owe”, folded per category across every template application rather than per application, so a later clone naming a different template cannot hide a category an earlier one could not write; its occurrence is the instant of the application that owes the category, so a repair applied by hand can be dismissed while a fresh refusal of the same category returns. Every item is **derived on each read** from the owning domains' own projections and nothing else — there is no work queue and nothing marks an item done, so completing the task, placing the session, retrying the delivery or publishing the page removes its item with no write anywhere and no possibility of the surface and the truth disagreeing. Each item carries a stable typed shape: a key, a category, a priority, a status, an owner where the source names one, a deadline where the source has one, and the console path that opens the condition. Authorization and degradation are `PRD-OPS-001`'s exactly: the request needs `events:read`, each category is composed under its owning domain's capability, a category the caller may not read is omitted and named as omitted, and a category that genuinely rejected reports its own correlated error while every other category stays usable and keeps its last good value. The **one** thing stored is a dismissal, because "I have seen this and am not acting on it" cannot be derived from anything else. A dismissal is per actor — one organizer may not silently remove work from a colleague's list — and its key carries the *occurrence* rather than the record, so re-deriving the same condition finds the dismissal while a genuinely new occurrence of it (a moved deadline, a further failed attempt) comes back. **Programme conditions carry an occurrence the agenda owns and maintains**: the board revision at which each session's placements last changed, and the one at which each time slot was last retimed, advanced in the same write that changes the board. An unplaced session's key carries its session's number and a conflict's carries the later of its two placements' and the two hours they sit in — so a session that is placed and taken off the board again, and a clash resolved and reintroduced between the same two placements or by retiming the slot beneath them, all come back open, while a dismissal survives every edit to a *different* part of the programme: another session's placement, a renamed or added room, any track edit, an added time slot, and a retiming of a slot this condition is not in. A session nobody has ever placed reads zero, which is the truth about it. Because the numbers are not backfilled, every programme dismissal recorded before they existed reads as occurrence zero and its item returns open once, which is the conservative direction: the surface asks about a condition again rather than hiding one nobody has seen. A dismissal is recorded only for an item the actor can currently derive on that event; anything else is a refusal rather than a stored row. Dismissed items stay visible, marked, and can be restored.

- `PRD-OPS-003` One append-only audit timeline records mutations worth remembering on an event, from the domains that declare a seam to observe, in one order. Five do today — content, review, agenda, communications and publishing — and each is observed through a port it declares itself and the composition root binds, so being on the timeline costs a domain no knowledge of auditing and no import of the platform domain. What is **not** recorded is as much a part of this clause as what is: CFP form transitions, CRM stage changes, event-settings edits, an organizer's own composed broadcast, and everything the one-minute tick does, because the scheduled entrypoint constructs no recorder at all. A record names when it happened, who did it, whether that was a person or a program, the action, what it acted on, and the correlation id of the request it happened under. **Append-only is structural**: storage refuses an `UPDATE` and a `DELETE` outright, so a record cannot be edited or removed by any code path, and a log a later write can rewrite is not evidence of anything. A replayed command produces exactly one record, enforced by a uniqueness constraint on a key derived from the *fact* rather than from the attempt. **Recording never fails the change it describes**: every writer is a consequence of something already durable, so a record that cannot be written is reported with everything needed to reconstruct it rather than raised — except where the record must commit *with* the fact, which is offered as a prepared record the caller appends to its own batch so that neither half can outlive the other. A record with no request behind it names nobody rather than inventing an identity — today that state is reached only by the agenda's publication batch, since no scheduled work records at all. **Attribution is request-scoped and structurally so**: the transport opens a scope on the request's identity before any route in any domain runs, whatever order the route modules are registered in, and ends it when the request ends, so a consequence that outlives its request names nobody rather than whoever was last through the door. Two requests overlapping on one identity holder — the shape a deployment reaches by constructing its services once and reusing them — is reported and attributed to nobody, because a record naming the wrong organizer is worse than one naming none and an append-only record cannot afterwards be corrected. The timeline is read by an organizer holding `events:settings:read` — it is the administrative view of an event rather than something every role on it may read — is scoped to one event, is paged by an opaque cursor over `(occurredAt, id)` so records sharing one instant page deterministically, and is bounded at 50 rows a page. A key is scoped to the event as well as the action and the target, because several targets a domain reports are only unique within an event. The idempotency key never leaves the server.

- `PRD-OPS-004` One **reporting surface** asks a bounded question of an event and shares the answer safely. A fixed catalogue of datasets — each named, each composed through the owning domain's public application interface under the capability that domain already enforces — is what a report may be built from, so the console can never offer a field the service would refuse. A definition is a dataset, a set of columns, filters over a closed operator list, an optional grouping and a sort; it is stored, named and re-runnable. Queries are bounded by a scan cap and refused as too expensive rather than run to exhaustion. **Personal columns are masked on the way out, never filtered out on the way in**: a filter evaluates against the unmasked value so a report can find a record without revealing it, and unmasking the output requires both the `reports:pii` capability and an explicit request on that run. Export is a *format applied to the same run* rather than a second path to the data — CSV and XLSX render from the rows the screen would have shown, through the same field-access decision, with a formula-injection guard on every cell. A report is shared by minting an expiring **capability link** rather than by granting anybody access: an opaque token whose hash alone is stored, optionally password-protected, with an expiry no further out than 30 days, an optional view limit, and revocation — the same shape `DEBT-012` records for every other capability URL in this repository. Scheduled delivery sends a link on a cadence, deliberately as an expiring link rather than as a message carrying data, and fires at most once per occurrence, enforced by a uniqueness constraint on the occurrence rather than by a timer nobody can replay.

For report capability links, password verification and finite-view spending are one atomic
write, so an absent or wrong password never consumes the holder's remaining view. A scheduled
delivery durably claims its unique occurrence before contacting the provider, then appends the
immutable result. An unmatched claim is shown as pending because it may be inside the provider
await or may have been interrupted; two overlapping ticks cannot both send it.
