# Bounded product specifications

Status: canonical | Owner: product | Last verified: 2026-08-12

## Events and access

- `PRD-EVT-001` One organization owns many events. Every event command names its organization or event scope, repositories constrain reads to the actor's organization memberships or event assignments, and event settings and records never leak across events. Organizers may create and switch among events in organizations they belong to, and an event-scoped organizer may rename an event or change its IANA timezone. Name and timezone remain events-domain data: publishing recomposes them into its draft on every preview, while the public snapshot in force changes only at the next site publish and its public slug changes only through publishing's separate address control. Organizations are this domain's records, so **self-serve provisioning is this domain's command**: a first-time sign-in that belongs to no organization is given one named after the person, and then a first event created through the ordinary authorized path with the organizer role it grants. Provisioning an organization is the single write here that names no actor, because at the moment it runs the caller has no membership to be authorized against — the organization is what they are about to become a member of; the caller has already established who is asking, and identity-access is the only caller. The two writes are not one transaction and are ordered so that a failure between them leaves a user holding an organization and no event, which the next sign-in completes rather than duplicating. The first event carries a placeholder name and the `UTC` timezone rather than asking for either in the flow: both are one-field edits on settings, and a wrong timezone guessed from a server-side redirect mis-renders every session time on the agenda.
- `PRD-EVT-002` An organization keeps named, versioned **event templates**: a capture of one event's *configuration*, reusable to set up the next occurrence. A template is saved from a source event the actor organizes, and each save is an immutable version recording which event and which person it came from, so an event configured from a template retains the exact version it was configured from as a stored fact rather than a claim. Organization-authorized rename, archive and duplicate exist; archiving retires a name rather than reserving it, and duplicating copies the newest version into a new template rather than re-stamping a history it did not live. A template read or applied across organizations answers exactly as an unknown one does — resolved through the events domain's own ownership query, never from a field in the request. **Applying is a second step, against an event that already exists**, because the actor's grant on a freshly created event does not reach the request that created it; the destination event's own `events:settings:update` is the grant that authorizes the write, and each configuration category additionally enforces its own domain's capability, so a category the actor cannot write is reported as unauthorized rather than silently skipped or raised as a fault. A preview lists every category that would be copied, excluded, or refused as incompatible, and writes nothing. **Events carry no dates** (`PRD-EVT-001`), so the destination range is confirmed as a parameter of the clone and every absolute time in the payload is remapped onto it in the destination's timezone; no deadline or slot time carries forward unchanged. Nothing derived from people or activity is ever copied: no submissions, evaluations, decisions, speaker or contact records, private files or comments, delivery attempts, audit history, published snapshots, credentials, provider secrets, or attendee itineraries. The categories are the CFP form and its routing, review's triage status set and scoring rubric, the agenda's rooms, tracks and time slots, the public page's summary and venue, the speaker portal's resource pages, and speaker task checklists. Message and reminder templates are already organization-scoped, so that category reports *already shared* and copies nothing rather than claiming a copy it did not make. Two of those need saying plainly. **Speaker task checklists did not exist before this**: every task in the system is bound to a real person, so a reusable checklist is a new content-owned concept — an ordered set of titled entries with a due date expressed as an offset, which an organizer later instantiates against named speaker profiles, and which is what a template carries rather than anybody's tasks. And **a cloned resource page's markup is sanitized again on import**, because a stored template payload is untrusted input by the time it is applied; an embed is refused unless the organizer authorizes its host in the destination, since that allowlist is an argument to the sanitizer at save time and is never stored. Applying is idempotent per category — repeating the same application converges rather than duplicating — and it is **not** atomic across domains: a category that fails leaves the categories that succeeded in place and says so, and re-applying is the repair (`ARC-FLOW-006`).
- `PRD-IAM-001` Roles are organizer, reviewer, speaker, and public. The current-session query returns the authenticated identity, organization memberships, event roles, and capabilities used by the application shell. Production sign-in has **two doors and one session**: an emailed six-digit code, and Google OIDC, each offered only where the deployment is configured for it and reported separately by the auth-config read so a surface never shows a door that cannot complete. Both issue the same signed, expiring HttpOnly cookie for the same identity, so memberships, event roles and capabilities are provider-blind; authenticated users may still mint a signed bearer identity restricted to one assigned event. Google sign-in is a redirect the browser follows and a callback it returns on, carrying per-attempt CSRF `state`, PKCE, and a `nonce`, and it trusts an `id_token` only after that token's signature, issuer, audience, expiry and `nonce` verify. A provider account is matched on the provider's own stable subject; failing that, on the **verified** address the token asserts, which links the sign-in to the identity that already holds it rather than creating a second one — a speaker who signs in with Google stays that speaker. An unverified address is refused, because a claimed address is an account-takeover primitive rather than an identity. A verified provider identity matching neither is a new account, provisioned per `PRD-EVT-001`. **An issued session is a durable record, and sign-out is revocation of it**: the cookie names a session row, every authenticated request checks that the row is present, unrevoked and unexpired, and signing out marks it revoked before clearing the cookie — so a copy of the cookie taken elsewhere, and any event-scoped bearer token minted from that session, stop being accepted on their next request. Sign-out still answers the same way whether or not a session was present, and reports no count, because either would tell an unauthenticated caller whether the cookie it presented was real. A signed-in person may also end **every** session the account holds, on every device, which does report a count because the caller proved that identity first. A session token issued before session records existed names no row and is refused, so the change signs everybody out once. Every identity state change is recorded in an append-only audit log written in the same database batch as the change, and no credential is ever recorded in it. **Organization membership is administered by its organizers.** An organizer may invite an address into their organization or onto one of its events, withdraw an invitation, remove a member, and grant or revoke a role on an event; each is authorized by the capability, membership of that organization, and that the capability was earned on one of its events, so a grant from one organization never reaches another. An invitation is accepted by the accepting session's own identity and never by matching the address it names, which is what keeps a seeded demo identity from being invited into a real organization; an unknown, expired, withdrawn or already-accepted invitation are one indistinguishable refusal. Removing a member or a role takes effect on their next request and does not end their sessions, because they may belong elsewhere. Every one of these actions, and every refusal of one, is recorded in the organization's own audit log, which its organizers can read. Development-only demo switching changes to a signed, expiring seeded identity; it does not bypass application authorization, and a demo deployment that also configures Google resolves both kinds of credential from the same cookie without ambiguity. `ADR-004` records why Google is an additional provider rather than a replacement.
  A demo persona may still use the ordinary single-session sign-out control: it clears the demo
  cookie and returns to the signed-out landing page. Only the separate **end every session** action
  is withheld, because a demo persona has no durable session rows to revoke.
- `PRD-IAM-002` Unauthenticated and unauthorized requests remain distinct, use the correlation-aware standard error contract, and reveal no inaccessible object details. The UI provides explicit loading, empty, denied, and recoverable error states, with navigation derived from the active event role. The two new surfaces state the same four. **Sign-in** loads the auth config before offering anything and shows nothing rather than a door that would 404; with no provider configured its empty state says the deployment offers no sign-in instead of presenting a dead button; a returning failure is one recoverable message that names no check, because which check refused is the attacker's answer and not the visitor's; and the denied state is the ordinary unauthenticated redirect. **A newly provisioned workspace** loads behind the same session read as every other surface, and its empty state is the point of it rather than an accident: no proposals, no sessions, no schedule, and a first action for each, so a workspace with nothing in it says what to do next instead of showing empty tables. **The members workspace** states the same four. Its loading state is per-read, so the members table and the audit log each say they are loading rather than blanking the page; its empty states name the first action — invite a co-organizer, or nothing has been recorded yet — rather than showing an empty table; a refusal is the console's ordinary recoverable notice carrying the correlation reference, announced where the control that caused it is; and the surface is withheld entirely from a persona that does not hold the capability. The invitation link is shown once, at the moment it is created, and says so: only its digest is stored, so no later screen can show it again. **Accepting** is its own surface, which the link resolves to and every signed-in person can reach — including a reviewer or speaker, who can reach neither event settings nor the members workspace, and who are who invitations are usually for. It reads the token out of the link so following one is the whole interaction, states a refusal with its correlation reference and leaves the token in place to retry, and on success sends the person into the workspace by a full document load, because the shell it was rendered in was built from a session read that predates the membership it just granted. **Ending every session** is offered beside sign-out and only to a real session — a demo persona is switched rather than signed out, holds no session record, and is refused the action by the API as well as denied the control. Its loading state is the same shared busy state that disables both controls; its success state is not a message but the landing page, reached by a full document load because the console it was pressed in is mounted around a session that no longer exists; and its failure state is the console's ordinary recoverable error notice, which names the correlation reference and leaves the person signed in rather than stranded.

## CFP, abstracts, and review

- `PRD-CFP-001` Organizers compose ordered typed fields, required rules, guidance, conditional visibility, category-based status routing, open/close state, preview, and publication. A visibility condition references an earlier question and is evaluated identically in the organizer preview, public applicant form, and server validation. Editable drafts use optimistic concurrency: every save names the version loaded by that editor, exactly one competing save advances it, and a stale save is refused without replacing the winner. Publishing and closing are separate decisions: publishing replaces the form applicants see and preserves whatever open/closed state the live call already had, so republishing a closed call never reopens it and only the explicit reopen action can. A first publication has no live state to preserve and opens the call.
- `PRD-CFP-002` Submission is server validated and idempotent; applicants get a durable confirmation identifier. Hidden fields are neither required nor accepted, and the first matching routing rule resolves a CFP-owned triage status that is persisted with the form-field snapshot rather than recomputed after form edits. It is the only unauthenticated write, so it is bounded: a submission carries at most 40 answers, each within the `maxLength` its published field advertises, and repeated submissions from one address are throttled. The counter is keyed on the caller's address alone — never on anything the caller supplies, such as the event id in the path — because a caller who can mint counter keys can evict its own spent counter and start again.
- `PRD-ABS-001` Organizers filter, assign, bulk-transition, and audit submissions through configured statuses.
- `PRD-REV-001` An evaluation plan defines criteria and scales. Reviewers see assignments, conflicts, completion, and no aggregate bias before submission.

`PRD-ABS-001` organizers configure an ordered event-scoped status set, filter proposals by those statuses, and transition a selected set atomically; each successful transition displays its transaction-current prior status, next status, proposal, actor, and occurrence time. The status set always contains the reserved decision statuses `accepted` and `declined`, which no configuration may remove; they are not transition destinations either. Reaching one of them is the *effect* of a recorded decision, so a transition into either is refused and names the decision command instead — a status change into `accepted` wrote a board state with no decision behind it, and the content domain then refused the very proposal the board showed as accepted. A proposal projection carries the submitter's name and contact address derived from the answers using the published form's field types; those details are organizer-only. The reviewer queue projection removes the derived contact object and replaces the derived display name with a fixed mask, and the answer list it carries never contains an `email`-typed answer or an answer whose field is identified as the submitter's name. That identification is a heuristic over the published form's own field types, ids, and labels, so it is exact only for details the form collected in a field it typed or labelled as such: an address a submitter types into a `short_text` answer, or a name inside a `long_text` biography, is not detected and still reaches the reviewer. Blind review is therefore a projection guarantee about identified fields, not a content scan. `PRD-REV-001` organizers configure numeric, dropdown, and free-text criteria with explicit weights; only numeric values contribute to the weighted aggregate, while every criterion value remains visible in organizer results and CSV export. Organizers may assign a proposal once per round to a user who holds the reviewer role for that event, or deterministically distribute a selected set across reviewers up to a per-reviewer cap. Advancing a status-filtered set creates the next numbered round; assignments, completed evaluations, and organizer outcomes remain round-scoped, so using the same reviewer again never overwrites prior-round history. The assignable list excludes the signed-in actor and the assignment command refuses that identity, because the organizer console exposes no reviewer queue, so assigning to oneself would create an evaluation nobody can open and would lock the rubric for good. Organizer progress names assigned, completed, and outstanding counts per reviewer. Bulk reminder delivery is deferred to issue #66 because communications has no reviewer-reminder trigger; review neither invents another lifecycle event nor writes communications tables. An organizer records an accept or decline decision on a proposal, which moves it to the matching reserved status and stores who decided, when, and why; that stored decision — not the status label — is what authorizes the proposal to become program content. The rubric is locked once assignments exist. An organizer may remove an assignment, which takes any draft evaluation and declared conflict with it and — when it was the last one — releases that lock, so a mis-assignment is a correctable mistake rather than a permanent freeze of the event's criteria; removal is refused once that reviewer has completed an evaluation, because its score is already counted in the proposal's aggregate and has emitted the completion event. Reviewers can access only their own event assignments, declare a conflict, save a validated draft, and complete it. A conflicted assignment cannot be evaluated; completion is terminal and atomically persists the evaluation, aggregate outcome, and one idempotent completion event. Reviewer responses never contain aggregate outcomes; organizers receive an outcome only after at least one completed evaluation in that round. Completion publishes version 1 of `EVT-REVIEW-COMPLETED` with organization/event/proposal/assignment scope and correlation/causation metadata.

## Speakers, content, and CRM

- `PRD-SPK-001` A person has one event-scoped speaker profile linked to sessions, tasks, assets, messages, and optional CRM origin.
- `PRD-CNT-001` A session owns title, abstract, format, speakers, tags/tracks, and publication state. It does not own a time: when and where a session happens is its placement on the event's *published* agenda, resolved through the agenda's public application interface every time a session is projected, so the speaker portal, the calendar export, and the published schedule can never name different times for one session. A session the published agenda does not place carries no schedule at all rather than a remembered or invented one, and a placement the organizer has moved but not yet published does not move it. Acceptance names only the proposal: title, abstract, format, and speaker identity are resolved through the review domain's public application interface and the speaker conversion port, so an unknown, foreign, or undecided proposal is refused and no caller supplies a speaker identity. Acceptance is idempotent per event and proposal, and the session stays editable afterwards. An organizer may withdraw a session, which removes it and every agenda placement holding it through that same interface — the reversal path for an abstract that was accepted and later declined — while the speaker's profile, tasks, and uploads survive, because one withdrawn session is not a reason to delete a person's work; the withdrawn session leaves the public page at the next publish, since published snapshots are immutable.
- `PRD-SPK-002` The portal is task-first and exposes completion, due state, profile preview, uploads, headshot selection, and calendar download. A speaker names which of their own uploads is their headshot, and an organizer of the event may name or remove it for them; nobody else may, and a file that belongs to another profile or is not an image is refused as a named field error. Naming a headshot is not publication: the chosen file keeps the visibility it had, the public gallery shows initials until an organizer marks that file publishable, and deleting the file clears the profile that pointed at it so no snapshot advertises a URL the asset route would refuse. The calendar download exists only while at least one session is scheduled, because an iCalendar object must carry at least one component; "scheduled" means placed on the published agenda, so the file a speaker imports carries exactly the instants and rooms the public schedule serves, and a session the published agenda does not place is left out of the file entirely rather than exported at an invented time. An organizer may also send one iTIP `REQUEST` per speaker and session. Repeating an unchanged send is idempotent, while every schedule or recipient-address change queues another `REQUEST` with the same `UID` and a strictly greater `SEQUENCE`, including a session returning to a time it held before, so a calendar client replaces the entry it currently holds. Uploads stay private until an organizer publishes them, and every publication is reversible: an organizer may return an asset to private, the uploading speaker or an organizer may delete it along with its stored bytes, and an asset is served anonymously only while its event's public page is live, so unpublishing the event withdraws what that page exposed. An asset a caller may not read is answered exactly like one that does not exist.

  Organizer-authored resource pages extend that portal. Body markup is sanitized through a strict parser-backed allowlist before storage, hidden pages never reach speakers, and reference embeds accept one HTTPS iframe only from the configured host allowlist. The browser renders that embed in a sandbox without script or same-origin privileges, while a refused host produces an actionable validation error.
- `PRD-CRM-001` Prospects have stage, contacts, notes, activities, owner, next action, and conversion preserving provenance. Ownership may only be given to a user identity-access reports as staffing that event — its organizers and reviewers — resolved through a public application query rather than a read of identity tables; an unknown or foreign-event owner is refused as a named field error, and being assignable grants no CRM access. Every stage transition appends exactly one `stage-change` activity naming the prior and next stage, written atomically with any note recorded by the same update.
  The CRM also holds an organization-wide **contact directory** spanning every event of one organization: searchable and filterable by company, title, tags, and custom fields, with those filters savable as named segments that store their definition rather than a frozen membership list. A person appears exactly once — enforced by a partial unique index on `(organization_id, email)` among un-merged records — and carries every event that has courted them, each event's stage read from that event's prospect so the directory can never claim a conversion the pipeline does not have. Contacts arrive by hand or by CSV import, which is previewed row by row against the live directory by the same code that then commits it, and which enriches rather than overwrites: a note somebody typed survives, the file's own values win where both name the same field, and a row that would *raise* a contact past what one may carry — twenty tags, thirty custom fields — is refused by name, in the preview as well as the commit, rather than applied by discarding something. A contact a merge has already left above that ceiling still accepts rows that add nothing to it. Near duplicates — the same person entered under a work and a personal address — are detected on name and company, and merging folds them into an explicitly chosen primary: nothing is deleted, history and event links move to the survivor, and the merged-away addresses stay searchable as aliases. One exception, because a contact holds at most one link per event: where both records were already sourced into the *same* event, the survivor keeps its own link and the loser's stays on the merged-away row. That row is retained, so no history is lost, but the survivor's event list shows one link for that event rather than two. Bulk outreach to a selection or a segment is previewed before it is sent and then delivered through communications' interface, which the CRM reaches through a port it declares itself and never by importing that domain. Organization-level metrics are counted over stored contacts, never constants.
  Directory access is authorized **at the organization**, and by three conditions together: `crm:manage`, membership of that organization, and that the capability was earned on an event *of that organization*. The third is what stops a capability granted by one organization from reading another's directory when the actor happens to belong to both (`ARC-AUTH-001`, issue #27). Sourcing a contact into an event additionally requires the event-scoped `crm:manage` and that the event belongs to the organization, so an organization-wide grant is never a licence to write into an event the actor does not run. Conversion continues to run through the existing idempotent speaker-conversion command with its existing key: pushing a contact into an event creates or reuses that event's prospect and converts *that*, so a contact pushed twice yields one prospect and one speaker and every provenance record written before the directory existed keeps its meaning.

## Agenda, communications, integrations, public

`PRD-SPK-001` at event scale includes CSV preview/import with explicit invalid and duplicate dispositions, persistent workflow/logistics/custom fields, and bulk assignment of general or file-request tasks. `PRD-SPK-002` associates uploads with requested tasks or sessions; re-upload creates a numbered latest version without withdrawing earlier readable versions. Speakers and organizers may leave attributed, timestamped asset comments. `PRD-CNT-001` records attributed immutable revisions before profile and session edits, and organizer restore writes another revision rather than erasing history. The revision and the edit it describes are written together or not at all, and the number a revision carries is allocated by that write, so two people editing one speaker are numbered in turn rather than one of them being refused (issue #116). Organizer ZIP export accepts selected latest deliverables only and emits deterministic names and contents. An event's **speaker checklist** — the ordered, titled lines `PRD-EVT-002` describes, each with a due date expressed as a signed day offset — is written and maintained from the content workspace: an organizer adds, reorders, edits and removes lines addressed by row, and separately instantiates the checklist against named speaker profiles, which is the act that creates dated tasks and tells those speakers about them. The two are separate on purpose, because declaring configuration and writing somebody's work are different decisions. A title another line on the event already holds is refused rather than converged on, and removing a line leaves tasks already assigned from it in place: a task is keyed by the title it was given and holds no pointer back, so once assigned the work is that speaker's. Instantiating is idempotent per speaker and line, so running it again after a speaker joins brings only the newcomer up to date — and so is the telling, so a second run announces nothing to the people it assigned nothing to. Recording a message, a comment or a revision still creates no notification or delivery effect of its own: what enqueues is a lifecycle *action*, through the port the domain taking it declares — content's for accepting a proposal and for requesting or instantiating a speaker's work, review's for a decision — and communications owns everything past that under `PRD-COM-001`.

- `PRD-AGD-001` The agenda manages event-scoped rooms, tracks, timeslots, and placements over sessions supplied by the content application query. A placement may be added, moved, or removed in a private draft. One assisted action seats the unscheduled sessions — every one of them, or exactly the subset the organizer selects — in a single draft revision, without introducing a conflict and without moving a placement made by hand; what it cannot seat stays unscheduled and says why, the control naming which of the two it will do, and the result is ordinary editable draft state. Overlapping placements explicitly identify every shared room, speaker, or session and give a resolution; a conflicted draft cannot be published. Publication is an organizer-only, auditable action that creates a numbered immutable snapshot. The agenda is also the single source of a session's time for every other domain: `ContentAgendaInterface` answers where the snapshot in force places each session, and withdrawing a session drops its draft placements, so no other domain stores a second copy of when a session happens. Only the latest snapshot—not subsequent draft edits—is available through the public schedule projection, and that projection carries the snapshot's number and publication time rather than its contents: the sessions it lists are the ones the event's published projection publishes, so a session on the board whose content is still a draft is never public and no room, track, slot, placement, session, or speaker storage identifier leaves the agenda.
- `PRD-COM-001` Templates and triggers enqueue immutable delivery attempts with retry and terminal state; sent history is auditable.
- `PRD-INT-001` SQL is canonical. Two integrations exist and each is one-way; naming them separately is the point, because they run in opposite directions over the same third party. **Outbound:** Airtable and Accelevents receive versioned projections through typed ports, and Greenroom owns every field they carry. **Inbound:** Accelevents is the registration platform of record, and its registrations are read into Greenroom as speaker profiles — the direction that eliminates manual re-entry, which is what the brief asks for. The inbound sync never writes another domain's tables: it goes through content's own public import command, so a preview writes nothing, a row is validated before it is accepted, and applying twice converges on the same speakers instead of duplicating them. Convergence is keyed on the **normalized email address**, through content's speaker-import ledger, rather than on the Accelevents record reference: two registrations sharing one address are therefore one speaker, which is the right answer for a person who registered twice and a deliberate departure from a per-record reading of idempotency. Registrants carry their Accelevents reference onto the profile they become, so provenance survives even where identity is collapsed. **Status:** outbound projection state, versioning and the outbox are implemented, and an HTTP adapter exists for each of the three delivery channels behind the credential-gated `COMMUNICATIONS_PROVIDERS=live` switch. The inbound sync is implemented with an organizer surface — preview, apply, last-run state and its failure — and runs on a deterministic in-repository roster by default, which is what lets the demo and a fresh clone sync with no credential. **Nothing here has reached a real Accelevents tenant:** no credential exists in this repository, every adapter test stubs `fetch`, and the staging smoke has not run, so a live sync's request shape is a documented contract rather than an observed one. The Airtable *product* surface the brief implies — organizer-visible field mapping, connection test, dry-run preview — still does not exist (`GAP-012`, issue #23's Airtable workflow).
- `PRD-PUB-001` Only published projections are public. Event hub, schedule, sessions, speakers, and CFP have direct and embeddable views. Preview and publish compose event metadata plus the published CFP, accepted-content, and agenda snapshots through their public application interfaces; publishing never reads another domain's tables. Publishing lazily creates storage for new events and copies that allowlisted composition into an immutable public snapshot, so later source edits remain invisible until the next publish. The public page's own fields — summary, venue, the two dates and the public address — are publishing's data and are edited on the publication draft rather than on any other domain's record: a typed date wins over the agenda-derived one and clearing it hands the field back to the agenda, and an address the organizer changes reaches visitors only at the next publish, so the snapshot in force and the URL serving it never disagree. The direct CFP applicant view reads the CFP domain's current published form and state, supports validated idempotent submission, and reflects close/reopen immediately. Every public address is a readable slug the projection step derives from the event name, session title, or speaker name, with a deterministic per-record uniqueness suffix: slugs are unique within an event, stable across republication of unchanged content, and never a storage identifier. The public schedule is addressed by the event's slug rather than its internal id and served only while the publication is live; it composes the agenda publication in force with the published projection, and takes every session it names — and every identifier it uses to name one — from that projection. Unpublishing removes the public snapshot immediately and public routes — the event hub, the schedule, and the assets that snapshot exposed — return the same not-published response used for unknown slugs. Attendees are anonymous and stay anonymous: an itinerary is a list of published session slugs addressed by an unguessable capability token, minted on demand, stored only as its SHA-256, and carried in the request path — never a cookie or a session, because the namespace's `Access-Control-Allow-Origin: *` forbids credentials and its shared-cache policy would serve one attendee's body from another attendee's request on a shared URL. The stable `/itineraries/:token` entry point resolves that capability before redirecting to the event's current public address, so an address change does not break a shared plan. Itineraries name only what the published projection names, are filtered against it on both write and read, and stop answering the moment the event is unpublished. Empty itineraries are pruned after 24 hours; every itinerary is pruned after its event's declared end plus a full UTC-day grace, so cleanup cannot interrupt the event. Populated plans otherwise have no expiry or revocation because their payload is only public-session slugs. Adding a name, an email address, a ticket, a payment, or any non-public data to an itinerary requires revisiting identity, retention and revocation before that field ships. Every public surface — event hub, schedule, sessions, speaker directory, speaker gallery and itinerary — reads the same published snapshot, so the fields describing one session agree across all of them, and each surface states that boundary rather than implying it is live. Embeds are configured by their own URL, and an embed honours only options it can validate. Public reads are cross-origin readable and cacheable only against a validator: every 200 carries a strong ETag and `no-cache`, so an unchanged representation costs a bodyless 304 while a withdrawal, close, or reopen is visible on the very next read. No public read carries a freshness lifetime, because a lifetime is precisely a window in which a cache would answer for a snapshot the organizer has already retracted; nothing that is not a public 200 is stored at all.
- `PRD-AI-001` AI may draft or summarize but never silently changes canonical state; manual fallback is required. A suggestion is offered to one reviewer for one assignment in one round, drafted from the same masked projection that reviewer reads — so the submitter's identity never crosses the provider boundary — and stored with the model, prompt version, time and abstract revision it came from, all four of which are shown to the reviewer with the draft. Nothing the provider returns is a score: suggestions are stored apart from evaluations and no aggregate reads them. A reviewer either dismisses a suggestion, which writes no evaluation and leaves only the audit row, or accepts it, which writes **their own evaluation as a draft** carrying the suggestion's id; completing that draft is a separate reviewer action and is the only thing that moves an aggregate. Storage enforces both halves rather than trusting the service: a suggestion cannot leave `offered` without a named responder, and an evaluation cannot claim a suggestion that is not its own reviewer's. The port is credential-gated with a deterministic fake as the default and an `off` mode that withdraws it entirely; a provider that is slow, throttled, unusable or absent surfaces as a visible notice beside a scoring form that still works, and a half-configured live mode refuses rather than silently drafting with the fake. **Status:** implemented and live-verified (issue #110, `GAP-011` closed). The 2026-08-13 staging smoke covered the deployed fail-safe, schema-valid generation and provenance, draft-only persistence, separate completion, failure normalization, manual fallback, and the identity-free outbound request; no credential exists in the repository and ordinary tests still stub the provider boundary.

## Operations across domains

- `PRD-OPS-001` One event-scoped search answers across every operational surface the caller can already open, and it is authorized **per source rather than per surface**. The request itself requires a session and `events:read` on the named event; each source inside it is then composed through the owning domain's own public application interface, under the capability that domain already enforces — sessions, speakers and tasks under `content:read`, proposals under `review:manage` for an organizer and `review:evaluate` for a reviewer, agenda placements under `agenda:manage`, deliveries under `communications:manage`, prospects and directory contacts under `crm:manage`. A source the caller may not read is **omitted and named as omitted**, never refused and never reported as an outage: the answer says which sections the caller's role does not include, and the sections that did answer stay usable. Any other rejection degrades exactly its own section, which reports its own correlated error while every other section still renders. There is no search index and no projection storage: private CRM notes, unpublished speaker material and reviewer-hidden aggregates keep their original rules by construction, because the only way this reaches them is the call the console itself would make. Blind review holds structurally — the reviewer projection is chosen by role rather than reached and recovered from, so a reviewer's results carry the masked submitter and never the organizer's. Results are scoped to the named event and carry no record of a sibling event in the same organization. Every hit carries the console path the server produced for it, including its event, because which surface a record opens depends on the role that read it. A query shorter than two characters is a field-level refusal rather than a scan, and every section is capped, so the cost of a keystroke is bounded. The surface states loading, empty, role-omitted and per-source-failed explicitly rather than rendering a heading over nothing.

- `PRD-OPS-002` One event-scoped operational inbox states everything waiting on an event, in five categories: agenda conflicts and unplaced sessions, outstanding speaker work, evaluations nobody has completed, deliveries that failed, and a public page behind what the organizer has composed. Every item is **derived on each read** from the owning domains' own projections and nothing else — there is no work queue and nothing marks an item done, so completing the task, placing the session, retrying the delivery or publishing the page removes its item with no write anywhere and no possibility of the surface and the truth disagreeing. Each item carries a stable typed shape: a key, a category, a priority, a status, an owner where the source names one, a deadline where the source has one, and the console path that opens the condition. Authorization and degradation are `PRD-OPS-001`'s exactly: the request needs `events:read`, each category is composed under its owning domain's capability, a category the caller may not read is omitted and named as omitted, and a category that genuinely rejected reports its own correlated error while every other category stays usable and keeps its last good value. The **one** thing stored is a dismissal, because "I have seen this and am not acting on it" cannot be derived from anything else. A dismissal is per actor — one organizer may not silently remove work from a colleague's list — and its key carries the *occurrence* rather than the record, so re-deriving the same condition finds the dismissal while a genuinely new occurrence of it (a moved deadline, a further failed attempt) comes back. The agenda projection is the documented exception: it exposes no occurrence or revision, so programme keys identify only the conflict or unplaced session and an exactly reintroduced condition remains dismissed (`GAP-022`). A dismissal is recorded only for an item the actor can currently derive on that event; anything else is a refusal rather than a stored row. Dismissed items stay visible, marked, and can be restored.

- `PRD-OPS-003` One append-only audit timeline records mutations worth remembering on an event, from the domains that declare a seam to observe, in one order. Five do today — content, review, agenda, communications and publishing — and each is observed through a port it declares itself and the composition root binds, so being on the timeline costs a domain no knowledge of auditing and no import of the platform domain. What is **not** recorded is as much a part of this clause as what is: CFP form transitions, CRM stage changes, event-settings edits, an organizer's own composed broadcast, and everything the one-minute tick does, because the scheduled entrypoint constructs no recorder at all. A record names when it happened, who did it, whether that was a person or a program, the action, what it acted on, and the correlation id of the request it happened under. **Append-only is structural**: storage refuses an `UPDATE` and a `DELETE` outright, so a record cannot be edited or removed by any code path, and a log a later write can rewrite is not evidence of anything. A replayed command produces exactly one record, enforced by a uniqueness constraint on a key derived from the *fact* rather than from the attempt. **Recording never fails the change it describes**: every writer is a consequence of something already durable, so a record that cannot be written is reported with everything needed to reconstruct it rather than raised — except where the record must commit *with* the fact, which is offered as a prepared record the caller appends to its own batch so that neither half can outlive the other. A record with no request behind it names nobody rather than inventing an identity — today that state is reached only by the agenda's publication batch, since no scheduled work records at all. The timeline is read by an organizer holding `events:settings:read` — it is the administrative view of an event rather than something every role on it may read — is scoped to one event, is paged by an opaque cursor over `(occurredAt, id)` so records sharing one instant page deterministically, and is bounded at 50 rows a page. A key is scoped to the event as well as the action and the target, because several targets a domain reports are only unique within an event. The idempotency key never leaves the server.
