# Bounded product specifications

Status: canonical | Owner: product | Last verified: 2026-08-09

## Events and access

- `PRD-EVT-001` One organization owns many events. Every event command names its organization or event scope, repositories constrain reads to the actor's organization memberships or event assignments, and event settings and records never leak across events. Organizers may create and switch among events in organizations they belong to.
- `PRD-IAM-001` Roles are organizer, reviewer, speaker, and public. The current-session query returns the authenticated identity, organization memberships, event roles, and capabilities used by the application shell. Production emailed-code sign-in issues a signed, expiring cookie, and authenticated users may mint a signed bearer identity restricted to one assigned event. Development-only demo switching changes to a signed, expiring seeded identity; it does not bypass application authorization.
- `PRD-IAM-002` Unauthenticated and unauthorized requests remain distinct, use the correlation-aware standard error contract, and reveal no inaccessible object details. The UI provides explicit loading, empty, denied, and recoverable error states, with navigation derived from the active event role.

## CFP, abstracts, and review

- `PRD-CFP-001` Organizers compose ordered typed fields, required rules, guidance, open/close state, preview, and publication. Publishing and closing are separate decisions: publishing replaces the form applicants see and preserves whatever open/closed state the live call already had, so republishing a closed call never reopens it and only the explicit reopen action can. A first publication has no live state to preserve and opens the call.
- `PRD-CFP-002` Submission is server validated and idempotent; applicants get a durable confirmation identifier. It is the only unauthenticated write, so it is bounded: a submission carries at most 40 answers, each within the `maxLength` its published field advertises, and repeated submissions from one address are throttled. The counter is keyed on the caller's address alone — never on anything the caller supplies, such as the event id in the path — because a caller who can mint counter keys can evict its own spent counter and start again.
- `PRD-ABS-001` Organizers filter, assign, bulk-transition, and audit submissions through configured statuses.
- `PRD-REV-001` An evaluation plan defines criteria and scales. Reviewers see assignments, conflicts, completion, and no aggregate bias before submission.

`PRD-ABS-001` organizers configure an ordered event-scoped status set, filter proposals by those statuses, and transition a selected set atomically; each successful transition displays its transaction-current prior status, next status, proposal, actor, and occurrence time. The status set always contains the reserved decision statuses `accepted` and `declined`, which no configuration may remove; they are not transition destinations either. Reaching one of them is the *effect* of a recorded decision, so a transition into either is refused and names the decision command instead — a status change into `accepted` wrote a board state with no decision behind it, and the content domain then refused the very proposal the board showed as accepted. A proposal projection carries the submitter's name and contact address derived from the answers using the published form's field types; those details are organizer-only. The reviewer queue projection removes the derived contact object and replaces the derived display name with a fixed mask, and the answer list it carries never contains an `email`-typed answer or an answer whose field is identified as the submitter's name. That identification is a heuristic over the published form's own field types, ids, and labels, so it is exact only for details the form collected in a field it typed or labelled as such: an address a submitter types into a `short_text` answer, or a name inside a `long_text` biography, is not detected and still reaches the reviewer. Blind review is therefore a projection guarantee about identified fields, not a content scan. `PRD-REV-001` organizers configure at least one uniquely identified, explicitly bounded scoring criterion and may assign a proposal once to a user who holds the reviewer role for that event, other than the organizer making the assignment: the assignable list a triage screen offers excludes the signed-in actor and the assignment command refuses that identity, because the organizer console exposes no reviewer queue, so assigning to oneself would create an evaluation nobody can open and would lock the rubric for good. An organizer records an accept or decline decision on a proposal, which moves it to the matching reserved status and stores who decided, when, and why; that stored decision — not the status label — is what authorizes the proposal to become program content. The rubric is locked once assignments exist. An organizer may remove an assignment, which takes any draft evaluation and declared conflict with it and — when it was the last one — releases that lock, so a mis-assignment is a correctable mistake rather than a permanent freeze of the event's criteria; removal is refused once that reviewer has completed an evaluation, because its score is already counted in the proposal's aggregate and has emitted the completion event. Reviewers can access only their own event assignments, declare a conflict, save a validated draft, and complete it. A conflicted assignment cannot be evaluated; completion is terminal and atomically persists the evaluation, aggregate outcome, and one idempotent completion event. Reviewer responses never contain aggregate outcomes; organizers receive an outcome only after at least one completed evaluation. Completion publishes version 1 of `EVT-REVIEW-COMPLETED` with organization/event/proposal/assignment scope and correlation/causation metadata.

## Speakers, content, and CRM

- `PRD-SPK-001` A person has one event-scoped speaker profile linked to sessions, tasks, assets, messages, and optional CRM origin.
- `PRD-CNT-001` A session owns title, abstract, format, speakers, tags/tracks, and publication state. It does not own a time: when and where a session happens is its placement on the event's *published* agenda, resolved through the agenda's public application interface every time a session is projected, so the speaker portal, the calendar export, and the published schedule can never name different times for one session. A session the published agenda does not place carries no schedule at all rather than a remembered or invented one, and a placement the organizer has moved but not yet published does not move it. Acceptance names only the proposal: title, abstract, format, and speaker identity are resolved through the review domain's public application interface and the speaker conversion port, so an unknown, foreign, or undecided proposal is refused and no caller supplies a speaker identity. Acceptance is idempotent per event and proposal, and the session stays editable afterwards. An organizer may withdraw a session, which removes it and every agenda placement holding it through that same interface — the reversal path for an abstract that was accepted and later declined — while the speaker's profile, tasks, and uploads survive, because one withdrawn session is not a reason to delete a person's work; the withdrawn session leaves the public page at the next publish, since published snapshots are immutable.
- `PRD-SPK-002` The portal is task-first and exposes completion, due state, profile preview, uploads, headshot selection, and calendar download. A speaker names which of their own uploads is their headshot, and an organizer of the event may name or remove it for them; nobody else may, and a file that belongs to another profile or is not an image is refused as a named field error. Naming a headshot is not publication: the chosen file keeps the visibility it had, the public gallery shows initials until an organizer marks that file publishable, and deleting the file clears the profile that pointed at it so no snapshot advertises a URL the asset route would refuse. The calendar download exists only while at least one session is scheduled, because an iCalendar object must carry at least one component; "scheduled" means placed on the published agenda, so the file a speaker imports carries exactly the instants and rooms the public schedule serves, and a session the published agenda does not place is left out of the file entirely rather than exported at an invented time. Uploads stay private until an organizer publishes them, and every publication is reversible: an organizer may return an asset to private, the uploading speaker or an organizer may delete it along with its stored bytes, and an asset is served anonymously only while its event's public page is live, so unpublishing the event withdraws what that page exposed. An asset a caller may not read is answered exactly like one that does not exist.
- `PRD-CRM-001` Prospects have stage, contacts, notes, activities, owner, next action, and conversion preserving provenance. Ownership may only be given to a user identity-access reports as staffing that event — its organizers and reviewers — resolved through a public application query rather than a read of identity tables; an unknown or foreign-event owner is refused as a named field error, and being assignable grants no CRM access. Every stage transition appends exactly one `stage-change` activity naming the prior and next stage, written atomically with any note recorded by the same update.

## Agenda, communications, integrations, public

- `PRD-AGD-001` The agenda manages event-scoped rooms, tracks, timeslots, and placements over sessions supplied by the content application query. A placement may be added, moved, or removed in a private draft. Overlapping placements explicitly identify every shared room, speaker, or session and give a resolution; a conflicted draft cannot be published. Publication is an organizer-only, auditable action that creates a numbered immutable snapshot. The agenda is also the single source of a session's time for every other domain: `ContentAgendaInterface` answers where the snapshot in force places each session, and withdrawing a session drops its draft placements, so no other domain stores a second copy of when a session happens. Only the latest snapshot—not subsequent draft edits—is available through the public schedule projection, and that projection carries the snapshot's number and publication time rather than its contents: the sessions it lists are the ones the event's published projection publishes, so a session on the board whose content is still a draft is never public and no room, track, slot, placement, session, or speaker storage identifier leaves the agenda.
- `PRD-COM-001` Templates and triggers enqueue immutable delivery attempts with retry and terminal state; sent history is auditable.
- `PRD-INT-001` SQL is canonical. Airtable and Accelevents receive versioned outbound projections through typed ports. **Status:** the ports, the versioned projection state, and the outbox are implemented, and an HTTP adapter now exists for each of the three channels behind a credential-gated `COMMUNICATIONS_PROVIDERS=live` switch, with the deterministic fake as the default everywhere else. No projection has reached a real provider: no credential for any of the three exists in this repository, the adapters' contract suite stubs `fetch`, and the staging smoke that would verify them has not run. The Accelevents *product* surface the brief names — organizer-visible mapping, dry run, sync state — still does not exist (`GAP-012`, issue #58).
- `PRD-PUB-001` Only published projections are public. Event hub, schedule, sessions, speakers, and CFP have direct and embeddable views. Preview and publish compose event metadata plus the published CFP, accepted-content, and agenda snapshots through their public application interfaces; publishing never reads another domain's tables. Publishing lazily creates storage for new events and copies that allowlisted composition into an immutable public snapshot, so later source edits remain invisible until the next publish. The direct CFP applicant view reads the CFP domain's current published form and state, supports validated idempotent submission, and reflects close/reopen immediately. Every public address is a readable slug the projection step derives from the event name, session title, or speaker name, with a deterministic per-record uniqueness suffix: slugs are unique within an event, stable across republication of unchanged content, and never a storage identifier. The public schedule is addressed by the event's slug rather than its internal id and served only while the publication is live; it composes the agenda publication in force with the published projection, and takes every session it names — and every identifier it uses to name one — from that projection. Unpublishing removes the public snapshot immediately and public routes — the event hub, the schedule, and the assets that snapshot exposed — return the same not-published response used for unknown slugs. Public reads are cross-origin readable and cacheable only against a validator: every 200 carries a strong ETag and `no-cache`, so an unchanged representation costs a bodyless 304 while a withdrawal, close, or reopen is visible on the very next read. No public read carries a freshness lifetime, because a lifetime is precisely a window in which a cache would answer for a snapshot the organizer has already retracted; nothing that is not a public 200 is stored at all.
- `PRD-AI-001` AI may draft or summarize but never silently changes canonical state; manual fallback is required. **Status:** unimplemented. No AI port, adapter, or fake exists in the codebase, and review is single-round; this specification is a constraint on future work, not a description of shipped behaviour (`GAP-011`, issue #57).
